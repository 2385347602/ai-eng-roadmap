26 · 内容安全与企业数据治理 ​

投入权重：6% · 新增一章。如果你要做知识库、客服、审核这类 ToB 产品，这一章决定你能不能过客户的合规评审。

上一版只有 09 · 安全 里的攻击防御，缺的是"产品化"这一层：审核怎么做成流水线、阈值怎么定、误杀了怎么申诉、数据从哪来到哪去谁负责。

先分清两件事 ​

这两件事经常被混着说，但负责的人、用的方法、考核的指标完全不同：

内容安全数据治理
管什么进入和输出的内容数据本身的资产属性
核心问题这条内容能不能放行这份数据从哪来、准不准、谁能看、什么时候删
关键指标漏放率 / 误杀率完整性 / 一致性 / 可追溯性
谁关心业务、法务客户 IT、审计

面试技巧：被问"你们怎么保证内容安全"，只答"接了审核 API"是初级；能答出"审核流水线 + 阈值分层 + 申诉闭环 + 审计留证"才是做过。

内容审核策略与风险分类 ​

  • 先分类，再定策略 必须 — 没有分类就没有策略。"涉政 / 涉黄 / 涉暴 / 违禁品 / 广告法 / 隐私 / 未成年"这几类，处置方式和容忍度完全不同。
  • 风险分级（高/中/低） 必须 — 高风险（涉未成年、涉恐）宁可误杀；中风险（擦边、辱骂）转人工；低风险（广告法用语）放行 + 事后抽检。能说出"分层阈值"就说明你想过真实业务。
  • 业务自定义类目 必须 — 通用审核 API 不懂你的行业。金融要管"承诺收益"，医疗要管"疗效保证"，教育要管"保过承诺"。这类必须自建词库 + 规则。
  • 审核策略文档化 重要 — 每个类目写清：定义、正例、反例、处置动作。这份文档是标注和申诉的唯一依据，没有它人工复核全是主观。
  • 边界案例要单独建档 重要 — 反讽、谐音、拼音缩写、方言、图片文字混合。这些是漏放的主要来源，要持续收集。
  • 合规要求的硬红线 必须 — 见 09 · 安全 的《生成式人工智能服务管理暂行办法》与生成内容标识要求。红线类目不允许"阈值可调"。

审核的技术手段 ​

  • 内容分类模型 必须 — 专用小模型（几百 MB）比大模型便宜几十倍、快几十倍。初筛必须用小模型，别用 GPT 判"这句话有没有脏话"。
  • Moderation API 必须 — 各厂商的现成审核接口。优点是免训练、类目全；缺点是类目固定、不可解释、有调用成本。适合冷启动。
  • 规则引擎 必须 — 关键词 / 正则 / 白名单 / 组合条件。规则不是落后技术——它对"确定要拦的东西"最可靠，且可解释、可审计。规则 + 模型双轨是行业标准做法。
  • 关键词的坑 必须 — 纯关键词会大量误杀（"杀人游戏"、"黄色笑话"里的颜色）。必须配白名单 + 上下文判断。
  • 哈希比对（指纹库） 重要 — 已知违规内容的哈希库，命中直接拦。对付重复传播最有效，成本几乎为零。
  • VLM 做图像审核 必须 — 图片里的文字、场景、人物都要判。注意 VLM 的幻觉：它会"看出"不存在的违规内容，高风险判定必须二次确认。
  • OCR + 文本审核的组合 重要 — 图片审核的一半工作量是"图里的字"。先 OCR 再走文本审核链路，比让 VLM 直接判更可控。
  • 音视频审核 必须 — 音频走 ASR 转文本再审核；视频抽帧 + 音轨分离，两路都审。成本高，所以必须先做初筛（时长、分辨率、抽样比例）。
  • 多模态融合判定 重要 — 图 + 文组合才违规的情况（正常图片配暗示性文字）。单模态分别审会漏，要做交叉判断。
  • 敏感信息检测（PII） 必须 — 身份证、手机号、银行卡、地址、人脸。用正则 + 校验位 + 命名实体识别三层，纯正则漏得多。
  • PII 脱敏 必须 — 送模型前替换成占位符（<PHONE_1>），需要还原时再映射回来。注意：脱敏后模型就答不了"这个用户是谁"，要按场景决定脱不脱。
  • 脱敏的可逆性设计 必须 — 映射表要和原文分开存、单独授权访问。脱敏表泄露等于没脱敏。

审核流水线 ​

一条能上生产的审核链路，长这样：

   ├─ 3. 规则引擎（硬红线关键词，命中即拦）

  • 顺序不能乱 必须 — 便宜的放前面。指纹和规则挡掉 60~80%，小模型挡掉剩下的绝大部分，大模型只处理边界。反过来做，成本会高一个数量级。
  • 输出审核同样重要 必须 — 用户输入干净不代表模型输出干净（尤其是 RAG 引用了脏文档）。双向审核，见 09 章。
  • 异步 vs 同步 必须 — 文本可以同步审（毫秒级）；图片、视频必须异步（秒到分钟）。异步要有"审核中"的中间状态，不能假装已通过。
  • 失败降级 必须 — 审核服务挂了怎么办？高风险类目默认拒绝（fail-closed），低风险类目放行并标记待审。这个选择必须显式写进设计文档，不能默认。
  • 审核耗时要进延迟预算 重要 — 同步审核加 200ms，用户能感知。要算进首字延迟，见 23 · 多模态 的延迟预算。

人工复核与申诉 ​

  • 人工复核队列 必须 — 按风险等级和等待时长排序。高风险优先，但也不能让低风险等太久（用户体验）。
  • 复核界面要给全信息 必须 — 原文 + 命中的规则/模型理由 + 相似历史案例。只给一句"疑似违规"的界面，复核员只能凭感觉。
  • 复核结果要回流 必须 — 人工判定进标注库，定期重训小模型或调规则。不回流，人工复核就是纯成本。
  • 双人复核机制 重要 — 高风险判定（封号、下架）要两人独立判。一致性低说明策略文档不清，先改文档。
  • 用户申诉入口 必须 — 被拦必须有申诉通道，且要说清拦的理由（不能只说"违反规定"）。这是合规要求，也是信任基础。
  • 申诉的时效承诺 必须 — 24 小时内响应之类。没有时效承诺的申诉通道等于没有。
  • 申诉数据的价值 重要 — 申诉成功的案例就是误杀样本，是调阈值最直接的依据。
  • 纠错闭环 重要 — 申诉成立 → 恢复内容 → 记录误杀 → 调阈值/改规则 → 回归测试。少一环，同样的问题会再犯。

阈值校准与效果度量 ​

  • Precision（精确率） 必须 — 拦下的里面有多少真该拦。低 = 误杀多，用户投诉。
  • Recall（召回率） 必须 — 该拦的里面拦住了多少。低 = 漏放多，合规风险。
  • False Positive（误杀） 必须 — 正常内容被拦。这是用户能直接感知的，投诉量主要来源。
  • False Negative（漏放） 必须 — 违规内容通过。这是监管能直接感知的，处罚主要来源。
  • 两个指标天然矛盾 必须 — 调高召回必然降精确。所以必须按类目分别定阈值，不能全局一个数。
  • 阈值校准的方法 必须 — 用一批人工标注样本，画 PR 曲线，按业务容忍度选点。别拍脑袋定 0.8。
  • 误杀率是产品指标 重要 — 要像看 DAU 一样天天看。误杀率突然上升通常意味着模型更新或规则改错了。
  • 抽检机制 必须 — 放行的内容也要抽样人工看。只看被拦的，你永远不知道漏了多少。
  • 审核策略版本管理 必须 — 规则、模型、阈值都要版本化。改了什么、什么时候改的、改了之后指标怎么变，必须能追溯。
  • 灰度发布审核策略 重要 — 新策略先在 5% 流量上跑，看误杀率和漏放率再全量。直接全量改阈值是事故高发动作。
  • 模型误判的处理流程 重要 — 发现系统性误判（某个词被误杀）→ 加白名单 → 记入回归集 → 下次训练带上。"个案修完就忘"是最常见的浪费。
  • 回归测试集 必须 — 至少几百条带标注的样本，每次改策略都跑。没有回归集的审核系统，改一次坏一次。

数据治理 ​

  • 数据资产目录 必须 — 有哪些数据、存在哪、谁负责、什么敏感级别。这是治理的起点，没有目录后面全是空谈。
  • 数据血缘（Lineage） 必须 — 一条回答引用了哪个 chunk、哪个文档、哪个原始来源。用户问"你凭什么这么说"，你要能一路追到原文。这也是 RAG 产品可信度的基础。
  • 数据质量校验 必须 — 完整性（有没有空字段）、一致性（同一事实多处是否一致）、时效性（多久没更新）、唯一性（有没有重复）。
  • 来源验证 必须 — 进知识库的文档要验：来源可信吗、谁上传的、有没有审批。"谁都能往知识库塞文档"是最危险的设计。
  • 数据分级 必须 — 公开 / 内部 / 机密 / 绝密。分级决定谁能检索到、能不能送外部模型。
  • 访问控制 必须 — 权限条件必须下推到检索层，不能检索后再过滤（见 09 · 安全）。
  • 数据保留策略 必须 — 每类数据定义保留期：对话记录 90 天、审计日志 1 年、原始文档跟随合同期。没有保留策略，存储成本会失控，合规也过不了。
  • 删除的完整性 必须 — 用户要求删除时，要删：主表、向量索引、缓存、备份标记、派生的摘要和记忆。少一处，"已删除"就是假的。
  • 软删除 + 冷静期 重要 — 立即硬删容易误操作，永久保留又不合规。折中：软删除 + 30 天冷静期 + 到期硬删。
  • 备份里的数据也要管 必须 — 备份不是法外之地。要有"从备份中清除指定数据"的流程，虽然麻烦但必须能答上来。
  • 数据出境 必须 — 用境外模型 API 就是出境。ToB 客户常直接禁止，这是选型第一道筛子。
  • 审计日志不可篡改 重要 — 谁在什么时候查了什么、改了什么、导出了什么。append-only 或写入独立存储。
  • 数据治理不是一次性项目 重要 — 要有责任人、有巡检、有指标。上线时治理得很好、半年后全是垃圾，是常态。

你会在面试里被问到的 ​

  1. "内容审核怎么做的？" — 答：指纹 → 规则 → 小模型 → 大模型四级流水线，按风险分级处置，输出也审，人工复核回流。说出"便宜的放前面"这个成本逻辑会加分。
  2. "误杀和漏放怎么权衡？" — 答：按类目分层定阈值，高风险宁误杀，低风险宁漏放 + 抽检。能说出"分层"就说明想过真实业务。
  3. "审核服务挂了怎么办？" — 答：高风险 fail-closed，低风险 fail-open + 标记待审。这个选择必须显式设计，不能默认。
  4. "用户申诉怎么处理？" — 答：入口 + 理由 + 时效 + 复核 + 回流调阈值 + 回归测试。六步说全，说明闭环做完了。
  5. "数据血缘怎么落地？" — 答：chunk 表带 document_id 和 page，回答带引用，能一路追到原文。这就是 RAG 的引用机制，你已经在 03 章 学过了。
  6. "用户要删除数据，你怎么保证删干净？" — 答：主表 + 向量索引 + 缓存 + 备份 + 派生数据，五处都要。能提"备份"就赢一半。

验收标准 ​

  • 能画出四级审核流水线，并解释为什么这个顺序最省钱
  • 能说出至少三类必须自建的业务类目，以及为什么通用 API 不够
  • 能解释 Precision / Recall 在审核场景的业务含义（误杀 vs 漏放）
  • 能设计一个申诉闭环，六步齐全
  • 能说出数据删除要覆盖的五处，以及"软删除 + 冷静期"的理由
  • 能解释数据血缘怎么和 RAG 引用机制打通
