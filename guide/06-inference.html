06 · 推理与部署 ​

投入权重：8% · 不需要会写 CUDA，但必须能算清"一张卡能扛多少并发、一次请求多少钱"。 这是从工程师到负责人的分水岭。

为什么应用工程师也要懂这个 ​

因为它直接决定产品形态。如果一次请求成本是 0.5 元，那你不可能做免费高频的 C 端产品；如果 TTFT 是 3 秒，那你必须设计"先出骨架"的交互。很多产品决策的约束条件，其实藏在推理成本里。

而且当老板问"为什么不用自己的模型"，你需要能给出一个有数字的答案，而不是"因为麻烦"。

推理引擎 ​

  • vLLM 必须 — PagedAttention 显存管理，工业界最主流。自部署首选。
  • SGLang 必须 — RadixAttention 前缀缓存，多轮与 Agent 场景吞吐优势明显。
  • TensorRT-LLM 重要 — NVIDIA 官方，极致性能但编译复杂。
  • llama.cpp / GGUF 必须 — CPU 与消费级显卡可跑，本地部署与端侧首选。
  • Ollama 必须 — 本地开发体验最好，生产不建议。
  • HuggingFace TGI 重要 — 官方推理容器，集成简单。
  • ONNX Runtime 重要 — 跨平台推理运行时，CPU/GPU/端侧都能跑。好处是脱离 PyTorch 依赖、启动快、内存小；坏处是导出有坑（动态 shape、自定义算子）。
  • 模型导出（ONNX / TensorRT engine） 选学 — 训练框架 → 推理格式。要处理动态 batch、动态序列长度、算子不支持三类问题。
  • CUDA 选学 — 知道它是 GPU 编程模型、知道 nvidia-smi 怎么看显存和利用率就够了。不用会写 kernel。
  • Triton（OpenAI 的 kernel 语言） 选学 — 用 Python 写 GPU kernel，比 CUDA 简单。了解存在即可，应用工程师基本用不到。

关键指标 ​

  • TTFT 首 token 延迟 必须 — 用户感知的"快不快"主要由它决定。目标 < 1s 是常见经验值，具体看场景。
  • TPOT / ITL token 间隔 必须 — 决定"读起来顺不顺"。目标 < 50ms/token 是常见经验值。
  • 吞吐 vs 延迟的权衡 必须 — 批处理提升吞吐但增加延迟。产品要哪个必须先定。
  • 并发数与显存 必须 — 并发 ≈ 可用显存 / 单请求 KV Cache。这是容量规划的核心公式。
  • 延迟分位数 重要 — 只看平均值会骗人，必须看 P95 / P99。
  • GPU 利用率 必须 — nvidia-smi 看两个数：显存占用和SM 利用率。显存满了但利用率低 = 被 KV Cache 卡住；显存没满但利用率 100% = 算力打满，该加卡或量化。
  • MFU（Model FLOPs Utilization） 选学 — 实际算力 / 理论峰值算力。训练看这个，推理一般不追求。
  • 批大小与显存的关系 必须 — KV Cache 显存 = 2 × 层数 × 头数 × head_dim × 序列长度 × batch × 精度字节。这个公式能让你当场算出"能不能扛 100 并发"，面试很加分。
  • OOM 的排查顺序 重要 — 先看是不是序列太长（KV Cache 爆），再看 batch 太大，再看是不是没开 PagedAttention，最后才怀疑模型太大。

优化技术 ​

  • Continuous Batching 必须 — 动态拼接请求，vLLM 的核心能力。
  • Prefix Caching 前缀缓存 必须 — system prompt 相同就能复用，多轮场景省一大截。
  • KV Cache 管理与分页 重要 — 理解为什么长上下文会挤爆显存。
  • 投机解码 Speculative Decoding 重要 — 小模型猜、大模型验，加速 2~3 倍。
  • 张量并行（Tensor Parallelism） 重要 — 把一个矩阵按列/行切到多卡，每卡算一部分再 all-reduce。单卡放不下时必须用，但卡间通信开销大，优先同机 NVLink，跨机很慢。
  • 流水线并行（Pipeline Parallelism） 重要 — 按层切分到多卡，形成流水。有"气泡"（bubble）导致利用率下降。
  • 数据并行（Data Parallelism） 重要 — 每卡一份完整模型，处理不同数据。训练常用，推理用多副本部署。
  • 专家并行（Expert Parallelism） 选学 — MoE 专用，不同专家放不同卡。DeepSeek 部署的关键技术。
  • P/D 分离（Prefill-Decode Disaggregation） 选学 — 把两阶段拆到不同机器，各自用最优配置。大规模部署的高级玩法。

量化与模型压缩 ​

  • GPTQ 重要 — 训练后量化，4bit 常见，需要校准数据。
  • AWQ 重要 — 激活感知量化，效果通常优于 GPTQ。
  • GGUF 量化等级 重要 — Q4_K_M 是性价比甜点，Q8 接近原精度。
  • FP16 / BF16 必须 — 都是 16 位。BF16 指数位多、动态范围大，训练更稳；FP16 尾数位多、精度高但容易溢出。推理一般用 FP16 或 BF16，看硬件支持。
  • FP8 重要 — H100 之后原生支持，精度损失很小，服务端性价比最高的选择。
  • INT8 / INT4 重要 — 整数量化，显存直接减半/减到四分之一。INT4 在 7B 级小模型上损失明显，在 70B 级上几乎无损。
  • 量化对效果的影响 必须 — 小模型量化损失明显大于大模型。要实测，别信"无损"宣传。测法：用你的评测集跑一遍量化前后，别只看公开 benchmark。
  • 剪枝（Pruning） 选学 — 去掉不重要的权重/注意力头。收益不稳定，工程上不如量化常用。
  • 蒸馏（Distillation） 重要 — 大模型教小模型。这是"把能力搬进私有小模型"最实际的路径，比剪枝靠谱。
  • 压缩手段的选择顺序 必须 — 先量化（最省事、收益最大）→ 再蒸馏（要训练）→ 再剪枝（收益不稳）。别一上来就研究剪枝。

硬件与成本 ​

  • 显存估算公式 必须 — 模型显存 ≈ 参数量 × 精度字节数。7B FP16 ≈ 14GB，加上 KV Cache 与框架开销要留余量。
  • GPU 选型 重要 — A100/H100 训练与高并发推理，L40S/4090 性价比推理，国产卡看生态。
  • 云 GPU 成本核算 必须 — 按小时算，再折算成"每千次请求成本"，这才是产品能用的数字。
  • Serverless 推理平台 必须 — 按 token 计费，免运维。量小时比自建便宜得多。
  • 自建 vs 调 API 的交叉点 必须 — 用你的真实 QPS 和 token 量算，别用别人的结论。通常量小的时候自建永远更贵。

网关层 ​

  • 模型网关 必须 — LiteLLM / OneAPI / OpenRouter：统一接口、多模型、计费、限流。
  • 多模型路由与降级 必须 — 主模型超时自动切备用，这是可用性的底线。
  • 限流与配额 必须 — 按用户/租户限流，防止单用户打爆成本。
  • 语义缓存 重要 — 相似问题直接返回缓存答案。省钱效果显著，但要设相似度阈值防答错。
  • 精确缓存 必须 — 相同请求直接命中，最简单有效。
  • 可观测与计费打通 重要 — 网关层是唯一能统一统计成本的地方，别把这事留给业务代码。
