15 · 面试题库 ​

160+ 道真实会问的题。每题给四个信息：考察什么 / 答题要点 / 会怎么追问 / 答错长什么样。

用法：先遮住答案自己说一遍，说不下去再看。能顺畅说出 80% 就算过关，剩下的按模块回去补。

使用说明 ​

面试不是背书，是证明你真做过。所以每道题的答案结构都应该是：

结论（一句话）→ 我的做法（具体）→ 为什么这么选（取舍）→ 结果（数字）

只说结论是背书，只有做法没有取舍是跟教程，有取舍没有数字是没量化。四段齐全，才像一个做过的人。

A · 通用与项目（10 题） ​

A1. 介绍一下你做过的最有代表性的 AI 项目 ​

考察：表达能力、项目真实性、你在项目里的真实角色。 要点：背景（什么业务问题）→ 你的角色（独立/主导/参与哪部分）→ 技术方案（两三句话）→ 结果（必须有数字）→ 一个坑。控制在 3 分钟。 追问：「这个方案是你定的还是 leader 定的？」「如果资源只有一半，你会砍掉哪部分？」 扣分：讲了五分钟技术细节但没有一个数字；或者说"我们团队做了"，全程没有"我"。

A2. 这个项目里，你做过最错的一个技术决定是什么？ ​

考察：有没有真复盘过。这题几乎无法编造。 要点：选一个真实但后果可控的错误。比如"一开始直接上语义分块，成本翻三倍效果没提升，后来回退到递归分块 + 父子块"。重点讲你怎么发现错了、怎么纠正的。 追问：「当时为什么没想到？」「后来怎么避免同类问题？」 扣分：「没犯过什么大错」——这等于说没做过；或者编一个"我太追求完美了"这种假缺点。

A3. 你怎么判断一个需求该不该用 LLM 做？ ​

考察：有没有产品判断力，会不会拿着锤子看什么都是钉子。 要点：三条标准——输入输出是否模糊（确定性任务用规则更便宜）、错误成本是否可承受（高则必须有人工兜底）、结果是否可验证（不可验证则无法迭代）。三条都过才做。 追问：「如果老板坚持要做呢？」（答：做一个小规模验证，用 50 个真实样本证明可行性或不可行，用数据说话） 扣分：「LLM 现在什么都能做」——这会被直接判定为没有工程判断。

A4. 模型答错了，你怎么定位是检索问题还是生成问题？ ​

考察：有没有分层调试的方法论。这是最核心的工程能力之一。 要点：看 trace。先看检索结果里有没有正确答案——没有就是检索问题（查分块、embedding、query 改写）；有但答案错了就是生成问题（查 prompt、上下文顺序、模型能力）。RAGAS 的 context recall 和 faithfulness 两个指标就是干这个的。 追问：「如果检索到了但模型没用，可能是什么原因？」（上下文太长被稀释、片段被放在中间位置、prompt 没要求必须基于材料回答） 扣分：「换个更强的模型试试」——这是没方法论的典型表现。

A5. 你的项目上线后，效果比测试时差很多，怎么排查？ ​

考察：有没有线上问题排查经验。 要点：先分类——是分布差异（线上问题更口语化/更长/更脏）还是工程问题（超时降级、缓存污染、版本不一致）。方法：抽样线上真实 query 做人工标注，和测试集对比；看延迟分位和错误分类。 追问：「怎么发现是分布差异？」（把线上 query 拿去跑测试集，看指标掉多少） 扣分：「再多加些 prompt 试试」。

A6. 如果让你重做这个项目，你会怎么改？ ​

考察：成长性和反思深度。这是判断"做过"还是"跟做过"的终极问题。 要点：至少说两条具体的：架构上的（"应该一开始就把检索和生成分开做评测"）和流程上的（"应该第一周就建评测集，而不是上线前才做"）。 追问：「为什么当时没这么做？」（诚实回答：不知道 / 赶进度 / 没人要求） 扣分：「没什么可改的，挺满意的」。

A7. 你怎么评估一个新模型要不要换？ ​

考察：选型方法论。 要点：六维打分——能力（跑自己的评测集）、成本（单位请求成本）、延迟（TTFT + TPOT）、上下文、多模态、合规（数据出境）。关键是用自己的评测集，不是看榜单。追问：「榜单分数高但你的评测集分数低，信哪个？」（信自己的，榜单的题分布和你的业务不同） 扣分：「看哪个分高用哪个」。

A8. 你和产品经理在方案上有分歧，怎么处理？ ​

考察：协作能力，以及能不能用工程语言沟通。 要点：把分歧转成可验证的问题——"你说的效果我理解，我们用 30 个真实样本跑一下，看能不能达到你要的水平"。用数据代替争论。 追问：「跑完发现达不到呢？」（给出替代方案：缩小范围、加人工审核、降低预期并明确告知） 扣分：「听产品的」或「坚持技术方案」。

A9. 你平时怎么跟进这个领域的新东西？ ​

考察：学习能力，以及信息源质量。 要点：说具体的一手源——官方文档 changelog、模型厂商博客、几个具体的人/仓库、arXiv 上特定方向。不要说"看公众号和短视频"。追问：「最近三个月你学了什么？」（必须能说出具体的东西和你的判断） 扣分：「关注了很多公众号」。

A10. 你为什么从前端转 AI？ ​

考察：动机的真实性和稳定性。 要点：不要说"AI 是趋势"。要说具体的观察——"我做前端时发现很多 AI 产品的交互烂到没法用，而这恰好是我擅长的；同时我发现缺的是能把模型能力做成可用产品的人，不是缺调模型的人"。 追问：「前端经验对做 AI 有什么帮助？」（流式渲染、状态管理、交互设计，这些是稀缺的） 扣分：「前端内卷，AI 有前景」——太功利，且暗示你会因为下一个风口再跳。

B · LLM 基础（20 题） ​

B1. temperature 和 top_p 的区别？什么时候调哪个？ ​

考察：是否真理解采样，还是只会复制参数。 要点：temperature 缩放 logits，改变整个分布的锐度；top_p 按累积概率截断候选集。两者都控制多样性但机制不同。实践中只调一个，同时改会无法归因。 追问：「temperature=0 能保证完全复现吗？」（不能。浮点累加顺序、批处理、GPU 非确定性、模型版本更新都会导致差异） 扣分：「温度越高越随机」就停——这是背概念，说明没实际调过。

B2. 为什么同一个 prompt 两次输出不一样？ ​

考察：对概率性系统的理解。 要点：采样是随机的（除非 temperature=0 且无其他随机源）；即使 temperature=0，浮点误差和批处理顺序也会导致微小差异，进而在分支点放大。 追问：「怎么让输出稳定？」（结构化输出 + 约束解码 + 后处理校验，而不是指望模型不随机） 扣分：「模型有 bug」。

B3. 上下文窗口 128k，为什么不能把所有文档塞进去？ ​

考察：成本意识和 lost-in-the-middle 认知。 要点：三个原因——成本随长度线性上升且长 prompt 更贵；延迟随长度上升；lost in the middle：关键信息在中段时召回显著下降。所以精准检索优于全塞。 追问：「那什么场景适合长上下文？」（少量长文档的整篇理解、跨文档对比，且文档数量可控时） 扣分：「窗口大就是为了塞更多」。

B4. 什么是 KV Cache？它和并发数什么关系？ ​

考察：是否理解推理的显存约束。 要点：自回归生成时缓存历史的 K/V，避免重复计算。它占用显存，显存除以单请求 KV 大小 ≈ 最大并发。上下文越长，单请求 KV 越大，并发越低。 追问：「Prefix Caching 和 KV Cache 什么关系？」（前缀相同时复用 KV，多轮场景省一大截） 扣分：「就是个缓存」。

B5. 中文的 token 怎么算成本？ ​

考察：有没有真算过钱。 要点：中文约 1 字 ≈ 1~1.5 token（经验值，必须用自己语料实测）；输入输出分开计价，输出通常贵 2~4 倍；缓存命中更便宜。实际成本 = (输入 token × 输入单价 + 输出 token × 输出单价) × 请求数。 追问：「你怎么降低单次成本？」（缩短 system prompt 以命中缓存、上下文压缩、小模型路由、语义缓存） 扣分：「按字数算」。

B6. 幻觉能彻底解决吗？ ​

考察：对能力边界的认知，以及会不会过度承诺。 要点：不能。分两类——事实性幻觉（编造事实）和忠实性幻觉（不忠于给定材料）。RAG 主要解决后者；前者只能靠检索 + 引用 + 免责提示降低概率。任何声称"零幻觉"的方案都不可信。 追问：「那产品上怎么处理？」（强制引用、置信度提示、关键结论人工复核） 扣分：「用 RAG 就能解决幻觉」。

B7. 为什么模型算不对大数乘法？ ​

考察：是否理解 tokenization 的影响。 要点：数字被切成 token 后丢失了位值结构，模型在做的是模式匹配而非运算。解法：让它输出表达式交给代码执行，或用工具调用。 追问：「还有哪些类似的坑？」（计数、字符串长度、日期计算、排序） 扣分：「模型不够强」。

B8. 指令遵循和格式遵循有什么区别？ ​

考察：有没有被 JSON 格式坑过。 要点：听懂要求 ≠ 能稳定输出合法结构。格式遵循需要 structured output / function calling / 约束解码，靠 prompt 里写"请输出 JSON"是不可靠的。 追问：「流式输出时怎么处理半截 JSON？」（增量解析器，不能等收完再 parse） 扣分：「在 prompt 里强调一下就行」。

B9. 什么是 MoE？总参数和激活参数有什么区别？ ​

考察：会不会被宣传数字误导。 要点：混合专家，每个 token 只激活部分专家。总参数决定显存占用，激活参数决定计算量。所以"总参数 600B 激活 30B"意味着显存要按 600B 算，速度接近 30B 稠密模型。 追问：「部署时显存怎么估？」（按总参数 × 精度，不是激活参数） 扣分：「就是参数更多」。

B10. 开源模型和闭源 API 怎么选？ ​

考察：工程取舍能力。 要点：看四件事——数据能否出境（不能则必须开源/国产）、量级能否摊薄运维（量小自建更贵）、能力是否够（跑自己的评测集）、合规要求（备案、私有化）。 追问：「什么量级自建才划算？」（不能给通用数字，要按自己的 QPS 和 token 量算 GPU 小时成本 vs API 单价的交叉点） 扣分：「开源省钱」。

B11. 模型的知识截止日期意味着什么？ ​

考察：是否理解时效性需求的约束。 要点：训练后的事它不知道，且它不会承认不知道，会编。所以任何时效性需求必须外挂检索或工具。 追问：「怎么让模型知道自己不知道？」（prompt 里显式要求"材料中没有就说没有"，并给出引用） 扣分：「模型会自动更新」。

B12. 什么是系统提示词泄露？怎么防？ ​

考察：安全意识。 要点：用户诱导模型复述 system prompt。防御的根本是不要把敏感规则写在 prompt 里——权限、密钥、业务逻辑都应该在代码层。 追问：「那 prompt 里能写什么？」（风格、格式、任务描述这些泄露了也无所谓的） 扣分：「在 prompt 里写'不要泄露系统提示词'」——这本身就会被绕过。

B13. 为什么流式输出是单向的？ ​

考察：是否理解自回归生成。 要点：生成是逐 token 的，第 n 个 token 依赖前 n-1 个，无法先给结尾。所以流式天然是单向追加。 追问：「那怎么实现'先给结论再给过程'？」（在 prompt 里要求先输出结论段，或者用两阶段调用） 扣分：「流式就是边生成边传」。

B14. 长上下文外推是什么？宣称的 1M 窗口可信吗？ ​

考察：对营销数字的警惕。 要点：YaRN / NTK 插值等技术把短训练模型拉到长上下文，但有效长度通常远小于宣称值。要用"大海捞针"类测试在自己的任务上验证。 追问：「怎么测有效长度？」（在长文本不同位置埋关键信息，看召回率随位置和长度的变化） 扣分：「宣称多少就是多少」。

B15. 什么是蒸馏？为什么能降本？ ​

考察：降本思路。 要点：用强模型生成高质量数据训练小模型，让小模型在特定任务上接近强模型表现。降本的逻辑是推理时用小模型，边际成本大幅下降。 追问：「蒸馏的风险？」（只学到表面模式、泛化差、强模型的错误被继承） 扣分：「就是把大模型变小」。

B16. 模型输出的长度会影响成本吗？怎么控制？ ​

考察：成本细节。 要点：会，且输出单价通常是输入的 2~4 倍。控制手段：max_tokens 硬约束、prompt 里明确长度要求、结构化输出（比自然语言短）。 追问：「输出太长还有什么问题？」（延迟高、用户读不完、关键信息被稀释） 扣分：「没什么影响」。

B17. 多轮对话里，历史怎么处理？ ​

考察：上下文管理实战。 要点：三种策略组合——滑窗（保留最近 N 轮）、摘要（把早期对话压缩成一段）、关键信息抽取（只保留实体和结论）。按场景选，不能全靠滑窗。 追问：「摘要会丢信息怎么办？」（关键实体单独存结构化状态，不依赖摘要） 扣分：「全部带上」。

B18. 什么是 prefix caching？对成本有什么影响？ ​

考察：是否优化过成本。 要点：相同前缀的请求复用已计算的 KV，命中部分按更低价格计费。所以 system prompt 要稳定不变、变量放后面，否则每次都不命中。 追问：「哪些做法会破坏缓存？」（在 system 里插入时间戳、随机 ID、用户信息） 扣分：「不知道这个」。

B19. 为什么模型会"过度拒答"？ ​

考察：对对齐副作用的理解。 要点：RLHF 阶段为了安全会给拒答高奖励，导致模型对边界情况过度保守。表现为正常问题也拒绝。 追问：「怎么缓解？」（prompt 里明确说明场景合法性、换更宽松的模型、把敏感判断放到代码层） 扣分：「模型太笨」。

B20. 你怎么给一个非技术同事解释"为什么 AI 有时会答错"？ ​

考察：沟通能力。 要点：用类比——它像一个读过很多书但没做过这份工作的人，能说出听起来合理的话，但不保证每个细节都对。所以重要的结论要核对来源。 追问：「那怎么让他信任这个产品？」（给引用、给置信度、明确边界） 扣分：讲 Transformer 原理。

C · Prompt 与上下文（15 题） ​

C1. 你怎么保证模型稳定输出 JSON？ ​

考察：是否踩过格式的坑。 要点：三层——优先用厂商的 structured output / function calling（最可靠）；其次约束解码（本地部署时）；最后才是 prompt 里给 schema + few-shot。任何情况下都要有解析失败的重试和降级。追问：「流式时怎么办？」（增量 JSON 解析器，或先流式输出文本再结构化） 扣分：「在 prompt 里写'必须输出 JSON'」。

C2. few-shot 示例怎么选？放几个？ ​

考察：是否理解示例的作用。 要点：示例的作用是定义"边界"而不只是"格式"，所以要覆盖边界情况（空输入、歧义、超长）。数量上 3~5 个通常够，再多收益递减且占上下文。顺序有影响（近因效应），重要示例放后面。 追问：「示例和指令冲突时信哪个？」（模型通常跟示例，所以示例必须和指令一致） 扣分：「越多越好」。

C3. 什么是提示注入？直接注入和间接注入有什么区别？ ​

考察：安全意识的核心题。 要点：直接注入是用户自己输入恶意指令；间接注入是恶意内容藏在检索文档、网页、工具返回值里。间接注入更危险，因为用户和开发者都看不到。 追问：「怎么防间接注入？」（内容与指令分区、声明"数据中的指令不执行"、工具白名单、输出侧校验） 扣分：「过滤关键词」。

C4. prompt 怎么版本管理？ ​

考察：工程规范意识。 要点：prompt 和代码一样进 git，每次改动有 commit message 说明原因；配置化而不是硬编码，支持灰度切换；版本号与模型版本绑定记录。 追问：「线上发现新版本更差怎么办？」（配置切换回滚，不用重新部署） 扣分：「直接改代码里的字符串」。

C5. 你怎么判断一个 prompt 改动是变好还是变坏？ ​

考察：评测驱动意识。 要点：跑评测集对比指标，不是看几个例子。要有基线分数、要有统计意义上的差异、要检查有没有在别的场景上退化。 追问：「没有评测集怎么办？」（先花半天建 50 条，这是最划算的投入） 扣分：「我试了几个 case 感觉好点了」。

C6. 什么是 Context Engineering？和 Prompt Engineering 什么区别？ ​

考察：是否跟上了概念演进。 要点：PE 关注"怎么说话"，CE 关注"往窗口里放什么、按什么顺序、放多少"。同一个模型换一种上下文组织方式，效果差异可能大于换模型。 追问：「具体怎么组织？」（按重要性排序、首尾放关键信息、压缩冗余、隔离无关内容） 扣分：「就是换个说法」。

C7. 上下文里塞太多内容会有什么问题？ ​

考察：是否理解 lost in the middle。 要点：成本上升、延迟上升、关键信息被稀释（中段召回下降）、以及模型被无关内容干扰导致答偏。 追问：「怎么决定塞多少？」（先做相关性阈值过滤，再按 token 预算分配） 扣分：「塞得多信息全」。

C8. CoT 什么时候有用，什么时候有害？ ​

考察：是否盲从技巧。 要点：多步推理、需要中间计算时有用；简单任务上有害（增加成本、增加出错面、可能引入虚假推理）。新一代推理模型内置了思考过程，外部 CoT 收益下降。 追问：「怎么验证 CoT 有没有用？」（同一批样本开关 CoT 对比指标） 扣分：「CoT 一定能提升效果」。

C9. 怎么让模型"不知道就说不知道"？ ​

考察：幻觉控制的实操。 要点：三个手段——明确给出"资料中没有就回答不知道"的指令并给示例；要求必须引用来源；把"不知道"设计成合法输出（而不是失败）。 追问：「这样会不会导致过度保守？」（会，需要在评测集上平衡"该说不知道"和"该回答"） 扣分：「模型会自己判断」。

C10. 负面指令为什么经常失效？ ​

考察：是否踩过这个坑。 要点：提到某个概念就会激活它（"不要提到 X"反而让 X 进入注意力）。改成正面表述："应该说 Y"。 追问：「那必须禁止某些词怎么办？」（用 logit_bias 或输出侧过滤，别靠 prompt） 扣分：「强调得不够狠」。

C11. 多轮对话里指代怎么解决？ ​

考察：RAG 与多轮结合的实战。 要点：用一次轻量模型调用做 query 改写，把"它""那个"补全成完整检索式。或者维护结构化会话状态（当前讨论的实体），改写时注入。 追问：「改写会增加延迟和成本，怎么权衡？」（用小模型，且只在检测到指代词时才改写） 扣分：「直接用原话检索」。

C12. 怎么控制模型的输出风格？ ​

考察：是否有风格对齐经验。 要点：prompt 里给正反例最有效；其次是 few-shot；如果要求非常稳定，就要微调。风格描述要具体（"每段不超过三句，不用形容词"）而不是抽象（"专业一点"）。 追问：「prompt 控制不住怎么办？」（微调，但先确认是不是描述不够具体） 扣分：「写'请专业一点'」。

C13. 你写过最长的 prompt 有多长？为什么这么长？ ​

考察：是否处理过复杂场景，以及有没有反思过 prompt 膨胀。 要点：诚实说。重点讲你怎么控制膨胀——拆分成多个调用、把稳定部分移到 system 以命中缓存、用代码处理能确定的逻辑。 追问：「prompt 越长效果越好吗？」（不是，超过一定长度后边际收益下降甚至变差） 扣分：「越详细越好」。

C14. 怎么让模型输出可溯源？ ​

考察：RAG 产品的核心设计。 要点：给每个检索片段编号，要求模型在句子后标注 [1]；后处理时把编号映射回原文位置；前端支持点击跳转。 追问：「模型标的编号不准怎么办？」（用更小的片段 + 明确要求，或者用后置的归因模型校验） 扣分：「让它说来源」。

C15. 你怎么处理用户输入超长的情况？ ​

考察：边界处理。 要点：前置检查 token 数；超限时要么截断（并告知用户）、要么分段处理再合并、要么走摘要。绝不能直接发出去等报错。 追问：「截断会丢信息怎么办？」（分段 + 逐段抽取要点 + 合并，成本高但完整） 扣分：「让 API 报错」。

D · RAG（30 题，面试重灾区） ​

D1. 你的 RAG 系统召回率多少？怎么测的？ ​

考察：最核心的验真题。答不上来基本等于没做过。 要点：必须给出具体数字和测量方法。标准答法：建 200 条"问题-正确文档片段"的标注集，计算 Recall@5 = 检索到的相关片段数 / 总相关片段数。然后说优化前后的对比。 追问：「标注集怎么来的？」「Recall@5 和 Recall@10 差多少？说明什么？」「Recall 高但答案还是错，为什么？」 扣分：「效果还不错」——没有数字就是没测过。

D2. 分块大小怎么定的？ ​

考察：是否做过对比实验。 要点：不能说"我用了 512"。要说：从 300~800 试了几档，用评测集测 Recall，发现 400 左右最好；同时用父子块解决"小块检索精准但上下文不足"的问题。并且说明这是在自己的语料上测的，不能通用。追问：「为什么太大不好？」（稀释相关性、浪费上下文预算）「太小呢？」（语义不完整、需要更多片段拼凑） 扣分：「按经验设的 512」。

D3. 为什么要加 rerank？不加会怎样？ ​

考察：是否理解两阶段检索。 要点：向量检索是 bi-encoder，query 和 doc 分别编码，快但精度有限；rerank 是 cross-encoder，把 query 和 doc 一起过模型，准但慢。所以召回 50 条用向量，精排取 5 条用 rerank。 追问：「rerank 的延迟增加多少？」「什么情况下不值得加？」（候选少、延迟极敏感） 扣分：「加了效果更好」——没有机制解释。

D4. 混合检索的权重怎么定的？ ​

考察：是否真的调过参。 要点：用评测集做网格搜索或简单的手动调，看 Recall 变化。常见起点是稠密为主、稀疏补充，但具体比例必须自己测。RRF 融合比加权求和更省调参。 追问：「什么场景下稀疏检索更重要？」（型号、代码、专有名词、精确匹配需求） 扣分：「各 50%」。

D5. 用户问"上个月的销售额是多少"，你的 RAG 怎么处理？ ​

考察：结构化与非结构化混合。 要点：这是数值查询，不该走文档检索。应该识别意图 → 路由到 SQL/API 查数 → 把结果交给模型组织语言。纯 RAG 会检索到某份报告里的旧数字，答错。 追问：「怎么判断该走哪条路？」（用路由模型或规则分类，也可以让模型先输出"需要什么数据"） 扣分：「检索相关文档然后让模型算」。

D6. 文档更新了怎么办？ ​

考察：索引一致性，生产事故高发点。 要点：用文档 ID + 内容 hash 做增量更新；删除要级联到向量库（否则会检索到已删除内容）；同一文档多版本共存会导致答案混乱，必须做版本替换而非追加。 追问：「怎么发现索引和源数据不一致？」（定期对账：源文档数 vs 索引 chunk 数） 扣分：「重新全量建索引」——量大了不可行。

D7. 权限怎么隔离？ ​

考察：ToB 场景必问，也是安全红线。 要点：权限条件下推到检索层（向量库的 metadata filter 或 partition），绝不能检索完再在应用层过滤——那样会泄露。三层隔离：数据、索引、缓存。 追问：「怎么测试有没有漏？」（用 A 租户账号问 B 租户的文档，必须问不出来） 扣分：「在 prompt 里告诉模型不要回答没权限的内容」。

D8. PDF 里的表格怎么处理？ ​

考察：数据接入的真实难点。 要点：表格是 RAG 最大的坑之一。方案：用 pdfplumber / MinerU 做版面分析；表格转 Markdown 保结构，同时生成一段自然语言描述用于检索；或者直接把页面当图用多模态检索（ColPali 路线）。 追问：「跨页表格怎么办？」（需要版面分析工具识别续表并合并） 扣分：「用 PyPDF2 抽文本」——表格会变成一堆乱序数字。

D9. 扫描件怎么处理？ ​

考察：是否处理过脏数据。 要点：OCR（PaddleOCR 中文强）或多模态模型直接读图。后者对复杂版面效果更好但更贵。关键是要做质量抽检——OCR 出来的错字会直接导致检索失败。 追问：「OCR 错了怎么办？」（关键字段做校验规则，或者重要文档人工校对） 扣分：「直接 OCR 就行」。

D10. 为什么用父子块？ ​

考察：是否理解检索精度与上下文完整性的矛盾。 要点：小块（如 200 字）检索精准但信息不全；大块（如 2000 字）信息全但相关性被稀释。父子块用小块建索引检索，命中后返回其所属的大块给模型。 追问：「父子块有什么代价？」（存储翻倍、需要维护映射关系） 扣分：「不知道这个概念」。

D11. query 改写有必要吗？ ​

考察：是否处理过真实用户输入。 要点：很有必要。真实 query 口语化、有错别字、有指代、太短或太长。改写手段：纠错、补全指代、扩展同义、生成多个查询。用评测集验证改写的收益。 追问：「改写会不会引入偏差？」（会，尤其是扩展时可能跑偏，所以要对比开关前后的指标） 扣分：「用户怎么问就怎么检索」。

D12. 检索到了正确内容，但模型没用，为什么？ ​

考察：分层调试能力。 要点：四个可能——上下文太长导致中段信息被忽略（调顺序）、prompt 没强制"必须基于材料"、片段被无关内容淹没、模型能力不足。 追问：「怎么验证是位置问题？」（把正确片段移到开头，看是否改善） 扣分：「模型不行」。

D13. RAG 和微调怎么选？ ​

考察：技术选型的判断力。 要点：知识不足用 RAG（可更新、可溯源）；格式/风格不稳用微调；降本用蒸馏。九成需求是 RAG。判断依据：知识是否频繁变化（变化则必须 RAG）、是否需要溯源（需要则必须 RAG）。 追问：「两个都要呢？」（先 RAG 保知识，再微调保风格，但成本高，要评估必要性） 扣分：「微调效果更好」。

D14. 多跳问题怎么处理？ ​

考察：是否处理过复杂查询。 要点：比如"对比 A 和 B 的政策差异"，需要先检索 A 再检索 B。方案：查询分解（拆成子问题分别检索）、迭代检索（第一轮结果提取新线索）、Agentic RAG（让模型决定检索几次）。 追问：「成本增加多少？」「怎么判断需要多跳？」（问题里出现多个实体或比较关系） 扣分：「一次检索搞定」。

D15. 你的向量库为什么选这个？ ​

考察：选型是否有理由。 要点：要给取舍。比如选 pgvector 是因为数据量百万级以内、已有 Postgres、需要事务和行级权限、不想多维护一套系统；如果到千万级或需要复杂过滤再考虑 Milvus/Qdrant。 追问：「pgvector 的瓶颈在哪？」（HNSW 索引构建慢、大规模下内存占用高、并发查询性能不如专用库） 扣分：「公司用的这个」。

D16. embedding 模型怎么选？ ​

考察：是否做过对比。 要点：中文优先 bge-m3 或 Qwen-Embedding；用自己的语料建小评测集对比召回；考虑维度（存储成本）、是否支持多语言、是否支持非对称检索。 追问：「换 embedding 模型要注意什么？」（必须全量重建索引，新旧向量不能混用） 扣分：「用 OpenAI 的」。

D17. 语义缓存会不会答错？ ​

考察：是否想过缓存的副作用。 要点：会。相似度高不等于答案相同（"上个月的销售额"和"这个月的销售额"向量很近但答案完全不同）。所以要设高阈值 + 排除时效性/数值类查询 + 缓存 key 带上时间等上下文。 追问：「阈值怎么定？」（用评测集测：阈值多少时误命中率可接受） 扣分：「相似度 0.9 就返回缓存」。

D18. 怎么评估检索质量？ ​

考察：指标体系。 要点：Recall@k（有没有找到）、MRR（找到的排第几）、NDCG（排序质量）。RAG 场景最关注 Recall@k，因为找不到就全错。 追问：「Recall 和 Precision 冲突怎么办？」（RAG 更容忍低 precision，因为 rerank 会过滤，但太低会浪费上下文预算） 扣分：「看最终答案对不对」——这是端到端，不能定位问题。

D19. 你的 chunk 里要不要加标题？ ​

考察：细节处理。 要点：要。每个 chunk 前面拼接所属章节路径（"第三章 > 3.2 退款政策 > ..."），能显著提升检索准确率，因为标题提供了上下文。 追问：「加了会不会重复浪费 token？」（会，但收益大于成本，可以只加最近两级） 扣分：「只存正文」。

D20. 多租户下索引怎么设计？ ​

考察：架构能力。 要点：三种方案——独立 collection（隔离最好但数量多时管理难）、共享 collection + partition（推荐）、共享 + metadata filter（最省但依赖库的过滤性能）。要评估租户数量和数据量。 追问：「租户数据量差异极大怎么办？」（大租户独立、小租户共享） 扣分：「每个租户一个库」。

D21. 为什么检索结果要去重？ ​

考察：是否注意到相邻块重复。 要点：分块有 overlap，相邻块内容高度重叠，不去重会占满上下文预算却只提供一份信息。用内容相似度或 MMR 做去重。 追问：「去重会不会误删？」（会，要设阈值，且保留来源最完整的那条） 扣分：「没考虑过」。

D22. 上下文怎么排序？ ​

考察：是否知道 lost in the middle。 要点：最相关的放首尾，次要的放中间。因为模型对首尾位置的信息召回更好。 追问：「怎么确定哪个最相关？」（rerank 分数） 扣分：「按检索分数顺序放」。

D23. 引用标注怎么实现？ ​

考察：产品细节。 要点：给每个片段编号，prompt 要求模型标注 [n]，后处理映射回原文位置（文档 ID + 页码/字符偏移），前端渲染成可点击。 追问：「模型标错了怎么办？」（用更明确的指令 + 后置校验，或者用专门的归因模型） 扣分：「让模型说来源」。

D24. RAG 系统的延迟怎么优化？ ​

考察：性能意识。 要点：分阶段看——检索（索引参数、减少候选）、rerank（模型大小、批处理）、生成（首 token）。可以并行化检索和 query 改写、用流式让用户先看到东西。 追问：「哪个阶段通常是瓶颈？」（生成的首 token，以及 rerank 如果模型太大） 扣分：「换个快模型」。

D25. 文档解析花多少时间？怎么提效？ ​

考察：是否真的做过脏活。 要点：通常是整个项目 50%~70% 的时间。提效手段：先做文档类型分类（原生 PDF / 扫描 / Office），不同类型走不同流水线；建解析质量的自动检查（乱码率、空块率）；抽样人工看。 追问：「怎么判断解析质量？」（抽 50 条看，或者统计异常指标） 扣分：「解析很快」。

D26. 用户问的问题和知识库无关，怎么办？ ​

考察：拒答设计。 要点：先做意图判断（相关性阈值），无关的直接引导而不是硬答。硬答会产生幻觉，比拒答更伤信任。 追问：「阈值怎么定？」（用评测集测，看误拒和误答的平衡） 扣分：「让模型自己判断」。

D27. GraphRAG 什么时候值得用？ ​

考察：是否盲目追新。 要点：适合全局性、关系性问题（"这批文档的主要矛盾是什么"、"A 和 B 有什么关系"）。普通事实问答用不上，且构建成本高（实体抽取 + 图构建 + 社区摘要）。 追问：「成本大概什么量级？」（构建阶段要跑大量 LLM 调用，比普通 RAG 高一个数量级） 扣分：「GraphRAG 效果更好」。

D28. 你的 RAG 上线后，用户反馈"答得不对"，你怎么查？ ​

考察：排查流程。 要点：按 trace 走——看 query、看检索到的片段、看 rerank 分数、看最终 prompt、看输出。判断是检索缺失、排序错误、还是生成没用。然后归类到 badcase 池，定期批量修。 追问：「怎么避免同类问题反复出现？」（badcase 回流进评测集，修完跑回归） 扣分：「重新调 prompt」。

D29. 为什么不能只用向量检索？ ​

考察：是否理解各检索方式的边界。 要点：向量检索对语义相似有效，但对精确匹配弱——型号"XR-2000"、代码函数名、人名，向量可能召回一堆语义相近但不对的内容。所以需要 BM25 补充。 追问：「反过来呢，只用 BM25 行不行？」（同义改写就失效，"怎么退款"和"退钱流程"匹配不上） 扣分：「向量检索最先进」。

D30. 如果给你 100 万份文档，架构要怎么改？ ​

考察：规模化思维。 要点：解析流水线要分布式（消息队列 + worker）；embedding 要批处理 + 限流；向量库要考虑分片与副本；检索要加缓存层；索引重建要能不停机（双写 + 切换）。 追问：「全量重建要多久？怎么估算？」（文档数 × 单文档处理时间 / 并发数） 扣分：「还是这套架构」。

E · Agent（20 题） ​

E1. 什么时候该用 Agent，什么时候用工作流？ ​

考察：最重要的 Agent 题。答错说明只会跟风。 要点：工作流优先。判断标准——步骤是否可预先枚举（可则用工作流）、路径是否依赖中间结果（依赖才需要 Agent）、错误成本是否可承受。Anthropic 的建议就是"先用最简单能work的方案"。 追问：「你的项目为什么用了/没用 Agent？」（必须有具体理由） 扣分：「Agent 更先进」——直接扣分。

E2. Agent 的单步成功率 90%，10 步之后是多少？ ​

考察：是否理解连乘衰减。 要点：0.9^10 ≈ 35%。这是 Agent 可靠性的根本约束。所以工程重点是减少步数、加校验点、允许回退。 追问：「怎么提升？」（减少步数、把确定性步骤交给代码、每步加验证、失败可重试） 扣分：「还是 90%」。

E3. 怎么防止 Agent 死循环？ ​

考察：可靠性设计。 要点：三层——最大步数上限、最大成本上限、无进展检测（连续 N 步没有产生新信息就终止）。三者都要有。 追问：「终止后怎么给用户交代？」（返回已完成部分 + 说明卡在哪 + 建议人工介入） 扣分：「设个最大轮数就行」。

E4. 工具调用失败了怎么处理？ ​

考察：错误处理设计。 要点：错误信息要能指导模型（"参数 date 应为 YYYY-MM-DD 格式，你传的是 2024/1/5"），而不是抛原始异常。然后区分可重试（超时）和不可重试（参数错误），前者退避重试，后者让模型修正参数。 追问：「重试会不会重复执行副作用？」（会，所以写操作要幂等键） 扣分：「catch 住返回 error」。

E5. 什么是 MCP？它解决什么问题？ ​

考察：是否跟进生态。 要点：Model Context Protocol，标准化"模型如何接入外部工具和数据"。解决的是 M×N 问题——以前每个模型要接每个工具，现在是 M+N。类比 USB 接口。 追问：「MCP 的架构？」（Host / Client / Server，stdio 和 HTTP+SSE 两种传输） 扣分：「一个新的框架」。

E6. 你怎么设计工具的描述？ ​

考察：工具设计经验。 要点：description 要写"什么时候用"和"什么时候不用"，参数要少、类型明确、必填项少。参数越多模型填错率越高。 追问：「工具太多模型选错怎么办？」（按任务域分组、用路由先选类别、减少工具数量） 扣分：「写清楚功能就行」。

E7. 高风险操作怎么处理？ ​

考察：落地经验。 要点：人工审批点（HITL）。发邮件、下单、删除数据这类不可逆操作必须插入确认。设计上要能暂停、展示将要执行的动作、等待确认、可取消。 追问：「审批会不会影响体验？」（分级：低风险自动、中风险事后可撤销、高风险必须确认） 扣分：「Agent 自己判断就行」。

E8. 多 Agent 有必要吗？ ​

考察：是否被概念带偏。 要点：多数场景没必要。多 Agent 的收益来自"能力差异"而非"角色扮演"，如果没有真正不同的能力（不同工具集、不同模型、不同知识），多 Agent 只是多花 token 且增加不确定性。 追问：「什么场景真的需要？」（需要并行探索、需要不同专业视角交叉验证、上下文必须隔离） 扣分：「多 Agent 效果更好」。

E9. Agent 的记忆怎么设计？ ​

考察：是否有长期记忆经验。 要点：分层——工作记忆（当前上下文）、情景记忆（历史事件）、语义记忆（事实）。关键是写入策略：不是所有对话都值得记，要有重要性判断；以及检索时机：每次全检索会污染上下文。 追问：「记忆冲突怎么办？」（时间戳 + 新覆盖旧，或并存让模型判断） 扣分：「存到向量库就行」。

E10. 怎么评估一个 Agent 的好坏？ ​

考察：评测思维。 要点：不能只看最终答案（路径不唯一）。要评三层——任务完成率、过程合理性（步数、是否绕路）、成本与延迟。还要有 trace 回放做人工评估。 追问：「过程合理性怎么量化？」（最优步数 vs 实际步数、无效工具调用比例） 扣分：「看它能不能完成任务」。

E11. Agent 的成本怎么控制？ ​

考察：成本意识。 要点：按任务设 token 预算；用便宜模型做简单决策、贵模型做难判断；上下文隔离避免膨胀；工具返回截断；缓存中间结果。 追问：「一个典型任务大概多少 token？」（要能说出量级） 扣分：「没算过」。

E12. 什么是 ReAct？ ​

考察：基础概念。 要点：Reasoning + Acting，思考-行动-观察循环。模型先输出思考，再决定调什么工具，拿到结果后继续思考，直到给出最终答案。 追问：「它和 Plan-and-Execute 的区别？」（后者先出完整计划再执行，适合步骤明确的任务，省 token 但不够灵活） 扣分：「一种 prompt 技巧」。

E13. 工具返回的内容太长怎么办？ ​

考察：上下文管理细节。 要点：截断 + 摘要 + 结构化提取。不能把 10KB HTML 直接塞回上下文。最好是工具层就返回结构化结果（只保留需要的字段）。 追问：「截断会丢关键信息怎么办？」（让模型先声明需要哪些字段，工具按需返回） 扣分：「直接返回」。

E14. Agent 怎么做沙箱？ ​

考察：安全意识。 要点：执行模型生成的代码必须隔离——容器/微虚拟机、无网络、限 CPU 和内存、限时、只挂载临时目录。 追问：「为什么必须无网络？」（否则可能被诱导外传数据或下载恶意代码） 扣分：「直接 eval」。

E15. 你的 Agent 怎么保证幂等？ ​

考察：生产经验。 要点：写操作带幂等键（任务 ID + 操作 ID），服务端去重；重试时复用同一个键；状态持久化，恢复时从断点继续而不是重头来。 追问：「幂等键怎么生成？」（不能用时间戳或随机数，要用业务唯一标识） 扣分：「重试就行」。

E16. 如果模型选错了工具怎么办？ ​

考察：容错设计。 要点：工具返回明确的错误或不相关信号，让模型有机会自我纠正；加一层校验（比如工具参数的业务规则校验）；关键路径上不要完全依赖模型选择。 追问：「怎么降低选错的概率？」（减少工具数量、描述写清边界、用路由预分类） 扣分：「模型会自己发现」。

E17. Agent 的上下文怎么隔离？ ​

考察：多 Agent 经验。 要点：每个 Agent 独立上下文，只交换结构化结论（不是完整对话）。否则一个 Agent 的错误会污染所有 Agent。 追问：「那怎么保证信息不丢？」（关键信息用结构化 schema 传递，而不是自然语言） 扣分：「共享一个上下文」。

E18. Computer Use 现在能上生产吗？ ​

考察：对新技术的现实判断。 要点：谨慎。稳定性不足（UI 变化、定位失败）、延迟高、成本高。适合有兜底的场景（人可接管），不适合关键路径。 追问：「什么场景适合？」（内部工具自动化、测试、低频高价值任务） 扣分：「可以，很成熟了」。

E19. 怎么让 Agent 可观测？ ​

考察：工程规范。 要点：每步记录输入输出、耗时、token、工具调用参数与结果。用 trace 串起来，能完整回放。Langfuse / LangSmith 这类工具。 追问：「回放的价值是什么？」（定位问题、做评测集、复现 bug） 扣分：「打日志就行」。

E20. 如果让你做一个"自动处理客服工单"的 Agent，怎么设计？ ​

考察：系统设计。 要点：先分类（意图识别）→ 简单问题走固定流程（工作流，不是 Agent）→ 复杂问题才进 Agent → 涉及退款等操作插入人工审批 → 全流程 trace → 失败降级到人工。 追问：「怎么评估效果？」（自动解决率、人工介入率、错误率、平均处理时长） 扣分：「一个 Agent 全搞定」。

F · 评测（20 题，第二重灾区） ​

F1. 你怎么评测一个没有标准答案的任务？ ​

考察：评测方法论。这是区分"做过"和"做好过"的关键题。 要点：三层——用 LLM-as-judge 按可执行的评分标准打分（不是"质量 1-5 分"）；建"必须包含的要点"和"必须避免的错误"清单做规则检查；人工抽检校准 judge。 追问：「judge 准吗？」（要先用 50 条人工标注校准，看一致率，低于 80% 不可信） 扣分：「人工看」或「没法评」。

F2. LLM-as-a-Judge 有什么偏差？怎么处理？ ​

考察：是否真的用过 judge。 要点：位置偏差（倾向选第一个 → 交换顺序跑两次取平均）、长度偏差（倾向长答案 → 评分标准里明确"简洁不扣分"）、自我偏好（同厂模型偏高 → 用不同厂模型做 judge）。 追问：「怎么验证 judge 可信？」（与人工标注的一致率、kappa 系数） 扣分：「用 GPT-4 评就行」。

F3. 你的评测集多少条？怎么来的？ ​

考察：验真题。 要点：起步 50~200 条，从真实日志采样（不是自己编题，自编会偏简单），覆盖简单/中等/困难分层，含边界与对抗样本。持续从线上 badcase 回流。 追问：「200 条够吗？」（够做相对比较，不够做绝对精度估计，看置信区间） 扣分：「几十条吧」或者「自己想的题」。

F4. 怎么证明你的改动确实有效？ ​

考察：实验设计。 要点：固定评测集 → 跑基线 → 改动 → 再跑 → 对比指标 → 检查有没有在其他维度退化 → 小流量灰度 → 看线上指标。 追问：「指标涨了 2% 算有效吗？」（要看样本量和波动，2% 在 200 条样本上可能不显著） 扣分：「我感觉好了」。

F5. 线上应该看哪些指标？ ​

考察：产品思维。 要点：采纳率（最硬）、任务完成率、人工介入率、重试率、成本/请求、延迟 P95/P99、以及负向指标（投诉率、放弃率）。 追问：「只优化采纳率会怎样？」（模型会变保守、输出变短，所以要配制衡指标） 扣分：「看 DAU」。

F6. RAGAS 的几个指标分别是什么意思？ ​

考察：工具掌握。 要点：Faithfulness（答案是否忠于材料）、Answer Relevancy（是否回答了问题）、Context Precision（检索内容信噪比）、Context Recall（检索是否覆盖了需要的材料）。 追问：「哪个最重要？」（Context Recall 和 Faithfulness，前者决定上限，后者决定可信度） 扣分：「不知道具体含义」。

F7. 评测要不要进 CI？ ​

考察：工程规范。 要点：要。prompt 或模型变更时自动跑回归，不达标不允许合并。成本高的评测可以只在发版前全量跑，日常跑子集。 追问：「CI 里跑评测很慢很贵怎么办？」（子集 + 并行 + 缓存 + 只在相关文件变更时触发） 扣分：「上线前手动跑一下」。

F8. 传统 NLP 指标（BLEU/ROUGE）为什么不能用？ ​

考察：基础认知。 要点：它们只看词重叠，语义正确但换个说法就判错，而 LLM 输出天然多样。用它们会系统性地惩罚好的改写。 追问：「那什么能用？」（任务特定规则 + LLM-judge + 人工） 扣分：「可以用 BLEU」。

F9. 怎么评测检索模块？ ​

考察：分层评测。 要点：单独评，不和生成混在一起。用"问题 → 应召回的片段"标注集，算 Recall@k、MRR、NDCG。 追问：「为什么要分开评？」（否则出问题无法定位是检索还是生成） 扣分：「端到端看结果」。

F10. 标注一致性怎么保证？ ​

考察：数据质量意识。 要点：先写标注手册（含边界案例）→ 试标 20 条 → 双人标注比对 → 算 kappa → 一致性低就改标准而不是怪标注员。 追问：「kappa 多少算可接受？」（一般 0.6 以上算中等一致，0.8 以上算好；具体看任务） 扣分：「一个人标就行」。

F11. 怎么建对抗测试集？ ​

考察：边界意识。 要点：按攻击面设计——超长输入、空输入、多语言混写、注入尝试、歧义问题、知识库外的问题、要求它做不该做的事。 追问：「多久更新一次？」（持续，每次发现新 badcase 就加） 扣分：「没做过」。

F12. 模型升级了，怎么验证没退化？ ​

考察：变更管理。 要点：跑完整评测集对比；重点看之前修过的 badcase 有没有复发；看延迟和成本变化；小流量灰度。 追问：「如果新模型整体更好但某些场景更差怎么办？」（按场景路由，不同场景用不同模型） 扣分：「直接换」。

F13. 用户反馈怎么用起来？ ​

考察：数据飞轮意识。 要点：显式（点赞点踩）+ 隐式（复制、采纳、重试、中断）。差评样本进 badcase 池 → 归因分类 → 修 → 进评测集 → 回归。要有固定节奏，否则池子会烂。 追问：「怎么避免只优化差评？」（也要看整体指标，差评可能只代表少数场景） 扣分：「收集了但没分析」。

F14. 怎么评估一个 prompt 的鲁棒性？ ​

考察：测试思维。 要点：同一意图用不同表达方式测（口语、书面、错别字、简写）；加噪声（多余空格、换行、无关前缀）；测边界（空、超长、多语言）。 追问：「鲁棒性差怎么改？」（加 few-shot 覆盖变体、结构化输入、前置清洗） 扣分：「测几个例子就行」。

F15. 成本怎么进评测？ ​

考察：单位经济。 要点：每次评测记录 token 和费用，算出"每提升 1% 指标的成本"。有些优化（比如加 rerank）提升明显但成本翻倍，要算 ROI。 追问：「怎么算 ROI？」（提升带来的业务价值 / 增加的成本，业务价值要产品给） 扣分：「只看效果不看成本」。

F16. 怎么评测多轮对话？ ​

考察：复杂场景。 要点：不能只测单轮。要测：上下文继承（第二轮的指代）、话题切换、纠正（用户说"不对，我是说..."）、长对话（10 轮后还准不准）。 追问：「怎么造多轮测试集？」（用真实日志，或者用模型模拟用户多轮提问再人工校验） 扣分：「按单轮测」。

F17. 你的评测集有没有过拟合风险？ ​

考察：方法论深度。 要点：有。反复用同一套集调参，指标会虚高。解法：留一份 holdout 集不参与调优，只在最终验证时用；定期补充新样本。 追问：「holdout 集多大？」（至少 20%，且要覆盖各难度层） 扣分：「没想过」。

F18. 怎么向老板证明这个 AI 项目有价值？ ​

考察：业务思维。 要点：用业务指标而非技术指标——节省了多少人力小时、处理量提升了多少、错误率下降多少、客户满意度变化。技术指标（Recall、Faithfulness）只是过程指标。 追问：「没有对照怎么算节省？」（上线前后对比、或者 A/B、或者人工基线） 扣分：「我们的准确率有 90%」。

F19. 评测和监控的区别？ ​

考察：概念清晰度。 要点：评测是离线的、用固定集、回答"这个版本比上个版本好吗"；监控是在线的、用真实流量、回答"现在系统正常吗"。两者互补，都要有。 追问：「线上能直接跑评测吗？」（可以，采样跑 judge，但成本高） 扣分：「是一回事」。

F20. 如果只能做一件事来提升 AI 项目质量，你做什么？ ​

考察：优先级判断。 要点：建评测集。因为它让所有后续优化有反馈信号，是复利最高的一件事。 追问：「为什么不是换更强的模型？」（换模型是赌博，评测是让每次改动都可验证） 扣分：「换个更好的模型」。

G · 部署与成本（15 题） ​

G1. 一次请求的成本怎么算？ ​

考察：是否算过账。 要点：输入 token × 输入单价 + 输出 token × 输出单价，加上检索、rerank、embedding 的调用成本。要给出具体量级。 追问：「怎么降到一半？」（缓存、上下文压缩、小模型路由、缩短 system） 扣分：「按 API 账单看」。

G2. TTFT 怎么优化？ ​

考察：性能优化。 要点：减少输入长度（尤其 system）、prefix caching、减少前置步骤（检索和改写并行）、用更快的模型、就近部署。 追问：「TTFT 和总延迟哪个更重要？」（首字延迟决定感知速度，总延迟决定完成时间，通常 TTFT 更影响体验） 扣分：「换个快模型」。

G3. 自建模型和调 API 怎么选？ ​

考察：成本建模。 要点：算交叉点。自建有固定成本（GPU 小时 × 24 × 30 + 运维人力），API 是边际成本。用你的真实 QPS 和 token 量算，量小自建永远更贵。 追问：「除了钱还看什么？」（数据出境、合规、可控性、能力上限） 扣分：「自建省钱」。

G4. 怎么防止成本被刷？ ​

考察：安全意识。 要点：按用户/租户限流与日配额；输入长度上限；Agent 的步数与 token 上限；异常检测（单用户突增告警）；关键接口加验证码或鉴权。 追问：「配额超了怎么办？」（降级到小模型或直接拒绝并提示） 扣分：「靠监控发现」。

G5. vLLM 为什么快？ ​

考察：推理框架认知。 要点：PagedAttention 把 KV Cache 分页管理，减少显存碎片，提升并发；Continuous Batching 动态拼请求，不让 GPU 空转。 追问：「SGLang 有什么不同？」（RadixAttention 做前缀共享，多轮和 Agent 场景吞吐更好） 扣分：「优化的好」。

G6. 量化会掉效果吗？ ​

考察：是否实测过。 要点：会，但程度取决于模型大小和量化方式。大模型 4bit 损失小，小模型损失明显。必须用自己的评测集测，不能信"无损"宣传。 追问：「什么量化方式推荐？」（服务端 FP8/AWQ，本地 GGUF 的 Q4_K_M 是性价比点） 扣分：「量化无损」。

G7. 一张卡能扛多少并发？ ​

考察：容量规划。 要点：并发 ≈ 可用显存 / 单请求 KV Cache。KV 大小与上下文长度成正比。所以长上下文场景并发会大幅下降。 追问：「怎么估算 KV 大小？」（与层数、隐藏维度、精度、序列长度相关，可以用引擎的显存分析工具） 扣分：「看情况」。

G8. 模型网关有什么用？ ​

考察：架构意识。 要点：统一接口（换模型不改业务代码）、多模型路由、降级（主模型挂了切备用）、限流、计费统计、日志。成本统计只能在这一层做才准。追问：「不用网关行不行？」（小项目可以，但多模型和成本管理会很痛） 扣分：「就是个代理」。

G9. 流式怎么实现？ ​

考察：前后端配合。 要点：后端 SSE 推送，事件类型区分 text-delta / tool-call / done / error；前端用 fetch + ReadableStream 或 EventSource 解析；要处理断线重连。 追问：「为什么不用 WebSocket？」（单向推送 SSE 够用，更简单，自动重连） 扣分：「用 WebSocket」。

G10. 长任务怎么处理？ ​

考察：异步架构。 要点：超过 30 秒的任务必须异步——提交任务返回 ID，后台队列处理，前端轮询或推送结果。要支持取消和进度。 追问：「任务丢了怎么办？」（持久化任务状态，重启后恢复） 扣分：「让用户等着」。

G11. 怎么保证高可用？ ​

考察：运维意识。 要点：多模型降级、超时熔断、重试退避、限流、多可用区、健康检查。关键是上游模型不可用时要有兜底。 追问：「兜底是什么？」（切备用模型、降级到检索结果直出、提示稍后重试） 扣分：「云厂商保证的」。

G12. 灰度怎么做？ ​

考察：发布规范。 要点：按用户 ID 哈希分流；新 prompt/模型/索引都支持灰度；监控指标达标再放量；随时可回滚（配置切换，不重新部署）。 追问：「灰度期间怎么对比？」（分流后对比两组的业务指标） 扣分：「直接全量」。

G13. 缓存怎么设计？ ​

考察：分层思维。 要点：三层——精确缓存（key 为规范化后的输入 hash）、语义缓存（向量相似，要设高阈值且排除时效性查询）、检索结果缓存。 追问：「缓存 key 要包含什么？」（模型版本、prompt 版本、用户/租户、时间相关上下文） 扣分：「按问题文本缓存」。

G14. 怎么压测 AI 服务？ ​

考察：测试能力。 要点：不能只压 QPS，要模拟真实 token 长度分布（长短混合）；观察 TTFT 和 TPOT 随并发的变化；找到拐点（延迟陡增的并发数）。 追问：「压测结果怎么用？」（定容量、定限流阈值、定扩容策略） 扣分：「用 ab 压一下」。

G15. 部署在云上还是私有化？ ​

考察：ToB 场景认知。 要点：看客户要求。金融、政务、医疗常要求私有化（数据不出内网）。私有化要考虑：模型选择（开源）、部署复杂度（容器化 + 一键脚本）、运维（客户自己维护，要极简）、升级方案。 追问：「私有化最大的坑？」（环境差异、GPU 型号不统一、客户网络隔离导致依赖装不上） 扣分：「云上就行」。

H · 安全与合规（10 题） ​

H1. 用境外模型 API 有什么合规问题？ ​

考察：合规意识。国内 ToB 项目必问。 要点：数据出境。用户输入会发到境外服务器，涉及个人信息出境的合规要求。ToB 客户常直接禁止。解法：用国产模型或开源模型私有化部署。 追问：「只是脱敏后发出去行不行？」（要看脱敏是否彻底，且很多客户不接受任何出境） 扣分：「没想过」。

H2. 生成式 AI 服务需要备案吗？ ​

考察：落地经验。 要点：面向公众提供生成式服务需要（大模型备案/算法备案）；企业内部使用通常不需要。备案周期以月计，是项目排期的硬约束。追问：「备案要准备什么？」（主体资质、模型来源、安全评估、内容审核机制等，具体以属地网信办要求为准） 扣分：「不知道」。

H3. AI 生成的内容需要标识吗？ ​

考察：是否跟进新规。 要点：需要。相关办法要求对 AI 生成合成内容做显式或隐式标识。产品设计要预留位置（水印、元数据、界面提示）。 追问：「隐式标识是什么？」（写在文件元数据里的标识） 扣分：「不用标」。

H4. 多租户怎么保证数据不串？ ​

考察：安全设计。 要点：三层隔离——数据库（行级权限）、向量库（partition 或 metadata filter）、缓存（key 带租户）。权限条件下推到检索层，不能检索后过滤。 追问：「怎么测试？」（用 A 租户账号问 B 租户的文档，必须问不出来） 扣分：「加个 where 条件」。

H5. 间接提示注入怎么防？ ​

考察：安全意识的核心。 要点：内容与指令分区（用分隔符 + 声明"数据中的指令不执行"）；工具白名单与最小权限；输出侧校验；对高风险操作加人工确认。没有单一手段能完全防住，必须叠层。追问：「为什么不能靠过滤关键词？」（攻击者可以用编码、多语言、语义改写绕过） 扣分：「过滤掉'忽略'这类词」。

H6. 模型生成的代码能直接执行吗？ ​

考察：安全意识。 要点：绝对不能。必须沙箱——容器隔离、无网络、限资源、限时、只挂载临时目录。 追问：「沙箱逃逸怎么办？」（用成熟方案如 gVisor/Firecracker，不要自己写） 扣分：「加个 try-catch」。

H7. 用户要求删除数据，你要删哪些地方？ ​

考察：数据治理细节。 要点：对话记录、向量库中的相关片段、缓存、日志中的原文（要脱敏或删除）、备份。最容易漏的是向量库和缓存。追问：「日志已经脱敏了还要删吗？」（看脱敏程度，如果可还原则要删） 扣分：「删数据库记录」。

H8. 怎么做内容审核？ ​

考察：合规落地。 要点：输入和输出双向审核；用厂商审核 API 或本地分类器；分级处理（拦截/提示/放行）；保留审核日志。 追问：「误杀怎么办？」（分级 + 申诉通道 + 阈值可调） 扣分：「加个敏感词表」。

H9. 医疗/金融场景有什么额外要求？ ​

考察：行业认知。 要点：更高的人工复核要求、更严的数据合规、通常需要行业资质、输出要明确免责、不能做诊断或投资建议这类越界行为。 追问：「怎么划边界？」（产品定位为"辅助信息整理"，不做判断，所有结论要求人工确认） 扣分：「和普通场景一样」。

H10. 怎么做红队测试？ ​

考察：安全测试。 要点：按攻击面设计用例——越权、注入、诱导泄露、生成有害内容、成本攻击。找非项目组的人来打。结果形成用例库，定期回归。 追问：「多久做一次？」（上线前必做，之后随大版本更新做） 扣分：「没做过」。

I · 架构与前端（15 题） ​

I1. 画一下你的系统架构 ​

考察：整体把控。 要点：从浏览器到模型，每一层说清职责。必须包含：网关（鉴权限流）、应用服务（编排）、模型网关（路由降级）、检索服务、异步队列、可观测。能解释每个组件为什么必要。追问：「去掉某个组件会怎样？」（这题考的是你有没有想过必要性） 扣分：画了一堆框但说不清职责。

I2. 流式渲染怎么避免卡顿？ ​

考察：前端硬功夫，你的优势区。 要点：不能每个 token 都 setState。用 buffer 累积 + requestAnimationFrame 批量刷新（比如 16ms 一次）；Markdown 用增量解析；代码高亮节流。 追问：「Markdown 半截怎么办？」（容错解析，未闭合的代码块先按纯文本渲染） 扣分：「用框架自带的」。

I3. 用户上滑查看历史时，新内容还在生成，怎么处理？ ​

考察：交互细节。这题很能区分有没有真做过。 要点：检测用户是否在底部附近，不在则不自动滚动，改为显示"有新内容"提示。用户回到底部再恢复跟随。 追问：「怎么判断在底部？」（scrollTop + clientHeight >= scrollHeight - 阈值） 扣分：「一直滚到底」。

I4. 长会话列表怎么优化？ ​

考察：性能。 要点：虚拟滚动；消息内容缓存（避免重复渲染 Markdown）；折叠长消息；分页加载历史。 追问：「虚拟滚动在变高消息上有什么问题？」（高度不定需要动态测量，滚动位置会跳） 扣分：「分页就行」。

I5. 引用溯源怎么做到可点击定位？ ​

考察：产品细节。 要点：检索片段带文档 ID + 页码/偏移；模型输出标注编号；前端解析编号渲染成链接；点击后打开原文并高亮对应位置。 追问：「PDF 怎么定位到具体位置？」（解析时记录每个 chunk 的页码和坐标，前端用 PDF.js 跳转） 扣分：「给个链接」。

I6. 怎么设计会话状态？ ​

考察：前端架构。 要点：会话列表 + 消息列表 + 当前生成状态；乐观更新（先显示用户消息再等响应）；中断状态；错误重试；草稿保存。 追问：「多标签页同时打开怎么办？」（用 BroadcastChannel 或服务端推送同步） 扣分：「一个数组存着」。

I7. AI 产品的空态怎么设计？ ​

考察：产品感。 要点：给示例问题（降低启动成本）；说明能力边界（能做什么不能做什么）；给快捷入口（上传文档、选模板）。这是流失最大的地方。追问：「示例问题怎么选？」（覆盖主要场景 + 一个"惊艳"的 + 一个"简单"的） 扣分：「放个输入框就行」。

I8. 错误怎么展示？ ​

考察：异常设计。 要点：分类——网络错误（可重试）、限流（告知等待）、审核拦截（说明原因）、额度用尽（引导充值）、模型异常（降级提示）。每种都要有明确的下一步动作。 追问：「审核拦截要不要告诉用户具体原因？」（说类别不说细节，避免被用来试探边界） 扣分：「统一弹个'出错了'」。

I9. 怎么处理超长回答的渲染？ ​

考察：性能。 要点：流式渲染本身就是增量；已完成的段落可以做 memo 避免重渲染；超长内容考虑折叠或分页。 追问：「代码块特别长怎么办？」（延迟高亮，或者虚拟化） 扣分：「一次性渲染」。

I10. 前后端流式协议怎么设计？ ​

考察：接口设计。 要点：SSE + 自定义事件类型。至少要区分：文本增量、工具调用开始/结束、思考过程、结束标记、错误。用 JSON 行格式便于扩展。 追问：「怎么保证兼容性？」（事件类型加版本号，前端忽略未知类型） 扣分：「就传字符串」。

I11. 怎么做多轮对话的上下文裁剪？ ​

考察：前后端配合。 要点：前端保留完整历史用于展示，但发给后端时按 token 预算裁剪。裁剪策略由后端决定（它知道模型限制），前端只负责传会话 ID。 追问：「裁剪逻辑放前端行不行？」（不行，前端不知道 token 数和模型限制，且容易被绕过） 扣分：「前端截断前 10 条」。

I12. 文件上传怎么处理大文件？ ​

考察：工程细节。 要点：分片上传 + 断点续传 + 前端预压缩（图片）；上传后异步解析，前端展示解析进度；解析失败要能重试。 追问：「解析很慢怎么办？」（异步 + 进度推送，不要让用户干等） 扣分：「直接传」。

I13. 怎么做 AI 产品的可访问性？ ​

考察：细节意识。 要点：流式内容用 aria-live 播报但要控制节奏（不能每个 token 都播）；生成状态要有文字说明；快捷键可配置；对比度达标。 追问：「aria-live 的 polite 和 assertive 怎么选？」（polite 用于流式内容，assertive 用于错误） 扣分：「加个 alt 就行」。

I14. 怎么做 Generative UI？ ​

考察：前沿理解。 要点：模型输出结构化描述（组件类型 + 属性），前端映射到真实组件渲染。关键是白名单——只能渲染预定义的组件，不能让模型输出任意代码。 追问：「安全风险是什么？」（模型被注入后渲染恶意组件，所以必须白名单 + 属性校验） 扣分：「让模型输出 HTML」。

I15. 前端怎么配合做 A/B 测试？ ​

考察：实验意识。 要点：分流由后端或配置中心决定（保证一致性）；前端上报曝光和转化事件；实验标识要能带到日志里便于归因。 追问：「前端分流有什么问题？」（不同设备/清缓存会导致分组不稳定） 扣分：「随机一下」。

J · 反问环节（必问，5 题） ​

面试最后一定会问"你有什么想问我的"。不问是减分项，问得不好也是。以下是按价值排序的问题。

J1. 这个岗位目前最大的技术挑战是什么？ ​

为什么问：能听出团队的真实水平和你将要面对的问题。如果对方说"模型效果不够好"，说明评测体系可能没建；如果说"成本压不下来"，说明已经过了 demo 阶段。

J2. 团队现在有评测体系吗？怎么做的？ ​

为什么问：这是判断团队成熟度的最强探针。有评测体系的团队，你进去能成长；没有的，你会重复踩坑。而且这个问题本身会让他们觉得你懂行。

J3. 我入职后前三个月，你希望我做出什么？ ​

为什么问：明确预期，避免进去后发现期待错位。也能听出这个岗位是"救火"还是"建设"。

J4. 这个产品现在的用户量和主要指标是什么？ ​

为什么问：判断项目是真做还是试验田。数据模糊通常意味着项目还不成熟。

J5. 团队怎么看"先做工作流还是先做 Agent"？ ​

为什么问：这是一个有立场的问题，能引发真正的技术讨论。对方的回答能让你判断团队是追概念还是讲工程。

不要问：加班多不多（可以问"团队的发布节奏是怎样的"）、薪资（HR 轮再谈）、"我表现得怎么样"（显得不自信）。

怎么用这份题库 ​

第一遍（自测）：遮住答案，每题说 30 秒。说不下去的标记出来。

第二遍（补漏）：标记的题回到对应模块章节，把知识点补上，再回来说一遍。

第三遍（模拟）：找人随机抽 10 题，连续说，模拟真实面试的疲劳感。真实面试到第 40 分钟时你的表达能力会下降，这一遍就是练这个。

判断标准：能顺畅说出 80% 就算过关。剩下 20% 允许不会，但要能诚实说"这块我没深入做过"——比编造强得多，面试官一眼能看出来。

最重要的一条：D 组（RAG）和 F 组（评测）是重灾区，这两组答不好，其他答得再漂亮也会被判定为"只跑过 demo"。优先攻这两组。
