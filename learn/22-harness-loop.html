第 1 / 6 步

Harness 是什么：模型之外的一切

Harness（脚手架）指模型之外、让模型能"真的干活"的那一整套东西。它包含五部分：

组成作用对效果的影响
工具集读文件、写文件、搜索、执行命令决定能力上限（不能跑测试就不知道对不对）
上下文管理哪些文件进上下文、怎么压缩、怎么检索决定它在长任务里会不会跑偏
循环控制什么时候继续、什么时候停、什么时候问人决定它会不会死循环或过早放弃
验证回路跑测试、跑类型检查、读报错决定它能不能自我修正
安全边界审批、沙箱、审计决定你敢不敢让它跑
★最关键的一条

有没有"验证回路"，是编码 Agent 的分水岭。 能跑测试的 Agent，会自己发现错误并修正；不能跑测试的 Agent，只能"看起来写完了"。这也是为什么命令行工具（能执行命令）普遍比纯对话（只能生成文本）效果好得多——不是因为模型强，是因为它能拿到反馈。

回答 checkpoint：IDE 里通常有更强的上下文（打开的文件、语言服务的类型信息、项目索引），CLI 里通常有更强的执行能力（能跑测试、能装依赖）。两边各缺一半，所以现在的趋势是融合——IDE 里加终端，CLI 里加语言服务。

前端经验类比
和 Vue 的运行时对照

模型像"组件的 render 函数"——它只负责算出结果。harness 像"Vue 的运行时"——负责调度、依赖追踪、更新、错误处理。没有运行时的 render 函数只是一段纯函数，什么都干不了。 同理，没有 harness 的模型只是一个文本生成器。

终止条件

补全编码 Agent 的终止判断。要求：只有验证通过才算成功；预算耗尽要中止；连续多轮没改文件也要中止。

function shouldStop(s, limits) { // 唯一"成功"的终止条件 if (s.lastVerify?.) return 'verified' // 预算 if (s.steps >= limits.maxSteps) return '' if (s.tokens >= limits.maxTokens) return 'token_limit' if (Date.now() - s.startedAt >= limits.maxWallMs) return '' // 空转检测 if (s.consecutiveNoChange >= ) return '' return null }

实现操作风险分级

实现 classify(action, workspace)。action 形如 { kind, path?, command? }，kind 为 read/search/write/run/delete/push。返回 safe / confirm / forbidden。规则：read/search → safe；write 且路径在工作区内 → safe，否则 forbidden；run 且命令在白名单（npm test、npm run build、npm run lint、tsc）内 → safe，其他 run → confirm；delete/push → forbidden。

阶段项目

项目一 · 知识库问答系统：迷你 Harness

这一课做一个 200 行的迷你编码 Agent，只服务于"给这个项目加功能"——它会成为你后面开发所有课程项目的加速器。

这一课要做的
  1. 实现四个工具：read_file（带 offset/limit 和总行数）、write_file（工作区内）、search（返回位置）、run_command（白名单 + 超时 + 输出截断）
  2. 实现主循环：读→想→做→验，验证步骤跑 `npm run check`，输出只保留失败部分
  3. 实现终止条件：verified / step_limit / token_limit / time_limit / no_progress
  4. 实现风险分级：read/search 放行，write 限工作区，run 限白名单，delete/push 禁止
  5. 实现子代理：一个只带 read+search 的 explore 代理，返回结论而非文件内容
  6. 实现审计日志：每次操作记录 sessionId、step、kind、target、risk
  7. 用这个 Agent 完成一个真实小需求（比如给项目加一个 health 端点），记录步数、token、耗时、人工介入次数
完成标志：给 Agent 一个"加 /health 端点并写测试"的任务，它能自己读文件、改代码、跑测试、看到失败、修正、再跑通过；故意让它删一个文件，被拒绝并记录到审计日志；对比"手动做"和"用 Agent 做"的实际耗时。
