部署与工程架构：让服务在别人的机器上稳定跑三个月

流式输出在本地好好的，上线后变成"等 8 秒一次性蹦出来"——这是 nginx 的锅。

0/7 步 · 0%
学完你能

能独立把 LLM 应用部署上线，并处理流式、并发、限流、降级、迁移这五类只有线上才会出现的问题。

前置知识
  • 学过第十课，有 trace 和成本数据
  • 能自己部署一个 Node 服务（会用 nginx / Docker 之一）
  • 跑通过一次真实的线上或准线上环境
本课 6 个学习目标
  1. 画出自己系统的部署拓扑，说清哪些组件有状态、哪些不能随便扩
  2. 解决流式响应在各层被缓冲的问题，让首字真的快
  3. 把服务做成无状态，能水平扩展且不丢会话
  4. 把长任务改成异步队列，并设计任务状态机与幂等
  5. 用令牌桶做限流，区分"排队"和"拒绝"两种策略
  6. 设计降级与回滚预案，让故障不至于变成事故
第 1 / 7 步

先画清拓扑：哪些能动，哪些不能动

LLM 应用的部署拓扑比普通 Web 应用复杂一点，因为多了一类"又慢又贵又有状态"的依赖。

典型拓扑与状态标注
[浏览器]
    │ HTTPS
    ▼
[CDN / 静态资源]          ← 无状态，随便扩
    │
    ▼
[负载均衡 / nginx]        ← 无状态
    │
    ▼
[Node API 实例 ×N]        ← 必须无状态！
    ├──► [模型 API]        ← 外部依赖，有限流
    ├──► [Postgres+pgvector] ← 有状态，不能随便扩
    ├──► [Redis]           ← 有状态，缓存/限流/会话
    └──► [任务队列]        ← 有状态
              │
              ▼
        [Worker ×M]        ← 无状态，可独立扩缩
组件有状态?能水平扩吗扩了会怎样
Node API否（改造后）能无影响
Worker否能要防重复消费
Postgres是只读副本可以写冲突、连接数爆炸
Redis是集群模式可以key 分布变了，缓存击穿
向量索引是（在 PG 里）随 PG重建索引期间查询变慢
会话取决于你放哪放 Redis 就能扩放内存就锁死单实例
×最常见的一号事故：会话存在进程内存里

开发时 const sessions = new Map() 很爽。扩到 3 个实例后，用户在实例 A 建立会话，下一个请求被负载均衡打到实例 B，会话丢失，表现为"随机掉登录"。更隐蔽的是流式场景：流式响应的连接是长连接，如果中途重试打到另一个实例，那边的上下文根本不存在。

还有一个 LLM 特有的点：模型 API 是"又慢又会失败"的外部依赖，它不是你的数据库。所以它必须被当作"可能随时不可用"的第三方来设计——超时、重试、降级、熔断，一样不能少。

算清并发与容量

模型 API 给你 100 RPM（每分钟请求数）。你的单次调用平均耗时 20 秒。要跑满这个配额，需要多少并发？如果每实例最多挂 50 个并发连接，至少要几个实例？

100 RPM = 请求/秒 每个请求占用 20 秒，所以稳态并发 = RPS × 平均耗时 = × 20 = 个并发 单实例上限 50 并发 → 至少需要 个实例（向上取整） （再留 30% 余量 → 建议 个）
  • 每秒请求数
  • 需要的并发数
  • 最少实例数
  • 留余量后的建议实例数

实现令牌桶

实现 take(bucket, n, now)，纯函数式令牌桶。bucket 形如 { tokens, last, capacity, rate }（last 和 now 是毫秒时间戳，rate 是每秒补充的令牌数）。返回 { allowed, bucket }，不要修改传入的 bucket。补充的令牌数不能超过 capacity。

阶段项目

项目一 · 知识库问答系统：上线

这一课把项目真正部署出去。产出物是一套可水平扩展、流式正常、有限流和降级、能安全回滚的部署方案。

这一课要做的
  1. 画出部署拓扑图，标注每个组件是否有状态、能不能水平扩、扩了要注意什么
  2. 把会话、限流计数、上传文件、定时任务全部外置，验证 3 实例下无状态
  3. 配 nginx：`proxy_buffering off` + HTTP/1.1 + 300s 超时 + gzip off，用 `curl -N` 和浏览器双重验证流式
  4. 加 SSE 心跳（15s）和 `req.on("close")` 的 abort，验证关页面后上游请求确实被取消
  5. 把"批量索引"改成异步任务：任务表 + 队列 + 状态机 + 进度 + 取消，验证 3 实例下同一任务只跑一次
  6. 实现令牌桶限流（Redis + Lua），按用户日额度 + 全局并发双维度；429 带 Retry-After
  7. 实现模型降级链：主模型 → 备用模型 → 纯检索结果，带 `degraded` 标记和监控打点
  8. 写一份发布检查清单，做一次两阶段数据库迁移演练（加列 → 双写 → 切读 → 删列）
  9. 演练一次回滚：把新版本发上去，再回滚到上一版，确认服务正常且数据没坏
完成标志：三个实例跑起来，用户随机刷新不掉登录；流式首字在 800ms 内出现；关掉浏览器标签后服务端日志显示上游请求被 abort；手动把模型 API 打成 503，系统自动切到备用模型并在面板上显示降级率；完成一次"发布 → 回滚"的完整演练。
