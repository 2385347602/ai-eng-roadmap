第 1 / 7 步

MCP 解决的真正问题：责任归属

表面上 MCP 解决的是 N×M 适配问题：N 个 AI 客户端、M 个工具，裸接入要写 N×M 份胶水代码，有了协议就变成 N+M。这是官方说法，也对，但它不是最重要的那部分。

真正重要的是"责任边界"。裸 function calling 里，工具是宿主应用的一部分——它的权限就是宿主应用的权限，它能读什么、能写什么，取决于宿主怎么实现。而 MCP Server 是独立进程/独立服务，它有：

  • 自己的身份：谁在调用我，我能验证。
  • 自己的权限：它能访问什么资源，由它自己决定，不继承宿主的全部权限。
  • 自己的日志：每次调用可独立审计，不依赖宿主记录。
  • 自己的生命周期：可以单独升级、单独下线、单独限流。
裸 function callingMCP Server
边界同一进程，共享全部权限独立进程/服务，权限隔离
复用每个宿主重写一遍一次实现，所有客户端可用
审计靠宿主打点服务端自己留完整日志
升级跟宿主一起发版独立发版
风险工具漏洞 = 宿主漏洞工具漏洞被进程边界限制
!反过来说：MCP 也放大了风险

一个恶意或有漏洞的 MCP Server，能读你的对话、能调它声明的一切工具、能把数据发到任意地方。装一个 MCP Server 的信任成本，约等于装一个浏览器插件。 这也是为什么"官方 MCP 市场"审核严格，以及为什么你自己写 server 时要格外注意最小权限。

前端经验类比
和浏览器插件对照

插件要声明权限（读所有网站 / 访问剪贴板），用户安装时能看到。MCP Server 也应该这样——它声明要什么能力，用户在安装时能看到并能拒绝。没有这层"声明-确认"，MCP 就只是个更方便的后门。

阶段项目

项目一 · 知识库问答系统：对外暴露 MCP Server

这一课把项目的检索能力包成一个 MCP Server，让别的 AI 客户端也能用你的知识库——同时把鉴权、审计、限流三件套补齐。

这一课要做的
  1. 实现 stdio 版本的 MCP Server，暴露 3 个工具（search_docs / read_doc / list_recent）+ 1 个 Resource（kb://doc/{id}）
  2. 用 Inspector 验证：工具列表正确、参数校验生效、错误返回结构化
  3. 改成 Streamable HTTP 传输，加 Bearer token 鉴权（签名 + 过期 + 受众校验）
  4. 按 scope 授权：只读 scope 不能调写工具；按 userId 限流（60 次/分钟）
  5. 实现审计日志：调用者、工具名、参数摘要（脱敏）、结果规模、耗时、状态
  6. 实现路径安全：realpath + resolve + relative 三重校验，用 10 个恶意路径测试
  7. 写 README：声明需要什么权限、访问什么数据、如何撤销授权、卸载后如何清理数据
完成标志：别的客户端（如 IDE 插件）能装上你的 server 并成功检索；用过期 token 调用返回 401；用低权限 token 调写工具返回 403；`../../etc/passwd` 被拒绝；审计日志里能查到每一次调用的完整记录。
