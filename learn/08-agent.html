第 8 课 · 进阶 · 约 85 分钟

Agent 智能体：让模型调用工具，且失败时能收场

Agent 的能力上限由工具决定，可靠性上限由熔断和权限决定。

0/8 步 · 0%
学完你能

能写出一个有明确边界、工具设计合理、失败可恢复的 Agent，并判断某个需求根本不该用 Agent。

前置知识
  • 学过第六课，能写出结构化的 prompt
  • 学过第七课，理解检索是 Agent 的一种工具
  • 调过 function calling / tool use 接口
本课 6 个学习目标
  1. 说清 Agent 和 Workflow 的本质区别，以及什么时候必须用后者
  2. 把工具设计成"模型能正确调用"的形状，而不是"人类觉得合理"的形状
  3. 理解 ReAct 循环每一步在做什么，以及上下文为什么会膨胀
  4. 给 Agent 装上步数、成本、时间三重熔断
  5. 设计人类确认点（HITL），让危险操作必须过人手
  6. 用 MCP 把工具暴露给别的客户端，并知道该暴露什么、不该暴露什么
第 1 / 8 步

Agent 不是"会思考的 AI"，是一个 while 循环

把 Agent 神秘化是理解它的最大障碍。去掉包装，一个 Agent 就是：

Agent 的全部机制
messages = [system, user]

while (true) {
  reply = llm(messages, tools)          ← 唯一的"智能"来源

  if (reply 没有工具调用) break          ← 终止条件

  for (call of reply.toolCalls) {
    result = execute(call)               ← 普通函数，没有智能
    messages.push(call, result)          ← 结果回灌，进入下一轮
  }
}

return reply.content

所有"智能"都在那一次 llm() 里，循环本身是笨的。 这个认知很重要，因为它告诉你优化的方向：要么改模型看到的东西（prompt、工具列表、历史裁剪），要么改工具的能力，改循环结构基本没用。

Workflow（工作流）Agent（智能体）
路径预先写死，A→B→C运行时决定，走几步、走哪条未知
可预测性高，每步都能画出来低，同样输入可能走不同路径
调试看日志就知道卡在哪要看完整对话轨迹才能复现
成本稳定，可估算波动大，可能 3 步也可能 30 步
适合步骤明确、需要审计、高频调用开放问题、需要探索、低频复杂任务
!最常见的架构错误

把明确流程做成 Agent。 "读工单 → 分类 → 查知识库 → 回复"这四步是固定的，写成 workflow 一百行代码、延迟 2 秒、成本可估。做成 Agent 之后：延迟 8 秒、成本 5 倍、偶尔跳步、出错难复现，而且没有任何收益——因为路径本来就是确定的。

前端经验类比
和 Vue Router 对照

Workflow 像静态路由表：路径写死，/user/:id 一定进 UserDetail。Agent 像运行时 router.push(动态计算的目标)：灵活，但你没法在构建时知道会去哪。能用静态路由解决的问题，不要用动态跳转。

给 Agent 装熔断

补全熔断逻辑。三重上限分别是步数、token 和时间，任何一个超了都要中止并返回已完成的部分。

const limits = { maxSteps: 12, maxTokens: 60000, maxWallMs: 90000 } while (true) { if ( >= limits.maxSteps) return abort('step_limit') if ( >= limits.maxTokens) return abort('token_limit') if (Date.now() - >= limits.maxWallMs) return abort('time_limit') const reply = await llm(messages, { tools }) steps++ tokens += reply.usage. if (!reply.toolCalls?.length) return { status: 'ok', answer: reply. } // ... 执行工具并回灌 messages }

  • token 变量
  • 起始时间变量

  • 模型的文本输出字段
编程挑战20 分练习 4 / 4

实现带校验的工具分发器

实现 dispatch(registry, name, args)。registry 是 { [name]: { run, schema } }，其中 schema 是一个有 safeParse 方法的校验器（zod 风格）。返回 { ok: true, value } 或 { ok: false, error, retryable }。规则：未知工具 → retryable: false；参数校验失败 → retryable: true 且 error 里包含字段名；run 抛错 → retryable: false，error 固定为 "工具执行失败"（不要把异常信息透出去）。

阶段项目

项目一 · 知识库问答系统：Agent 层

这一课给项目加一个可选的 Agent 层：在检索问答之外，支持"需要多步查询"的问题（比如先查订单再查知识库）。同时把工具、熔断、HITL 的规范定下来。

这一课要做的
  1. 定义 5 个工具：search_docs（复用第七课检索）、get_doc_detail、list_recent_queries、create_ticket、send_reply_draft
  2. 每个工具写清"何时用"的描述，参数用 zod 收敛，身份从服务端会话注入
  3. 实现 dispatch：参数校验 + 错误归一化 + retryable 判定 + 返回值截断
  4. 实现 runAgent：三重熔断（步数 12 / 60K token / 90s）+ 历史裁剪 + 重复调用检测
  5. 给 create_ticket 和 send_reply_draft 加 HITL：生成草稿，人工确认后才真正执行
  6. 写一个 20 条的轨迹测试集，断言"该调哪个工具""不该调哪个工具""超时后是否正确中止"
  7. 做一个对比实验：同一批问题，纯 RAG 一次调用 vs Agent 多步，比较准确率和平均成本
完成标志：能拿出对比数据说明 Agent 层在哪些问题上真的赢了（多步查询类），在哪些问题上白花钱（单跳问答类）；故意构造一个会让 Agent 死循环的输入，确认它在第 12 步或 90 秒时干净地中止并返回已完成的部分。
