TypeScript 类型工程：让编译器替你挡掉一半线上事故

类型不是写给人看的注释，是能在编译期证伪的约束。用错地方，它就是噪音。

第 1 / 8 步

为什么后端比前端更需要类型

前端写 TS，很多时候是"给自己的代码加注解"。数据来源是你自己调用的接口，出问题最多是页面白屏。

后端的处境完全不同：每一个入参都来自不可信的外部。可能是前端写错了、可能是别人用 curl 手搓的、可能是攻击者构造的、可能是三个月前的旧版本客户端。类型在这里的作用不是"注释"，是在边界上把 unknown 收窄成确定的形状。

位置数据可信度类型的价值
自己写的函数内部高低——主要是防手误
HTTP 请求体零高——必须在边界处收窄
数据库返回值中（列类型可信，但可空）高——null 是最常见的事故源
第三方 API 响应低高——字段可能缺失、改名、变类型
LLM 返回的 JSON极低极高——模型会编字段、少字段、多字段
★一句话定位

类型系统是你在编译期能免费跑的唯一一种测试。 它测的不是"逻辑对不对"，而是"形状对不对"——而形状错误占了线上事故的一大半。

前端经验类比
和 Vue 的 props 校验对照

Vue 的 defineProps<{ id: string }>() 只在开发期警告，运行时该崩还是崩。TypeScript 的类型同理——它不产生运行时保护。所以真正需要保护的地方（HTTP 入口），必须同时有类型和运行时校验，这就是这一课后面讲 zod 的原因。

填空：补全一个流式事件类型

这是一个 SSE 流式事件类型。补全缺失的部分，让"漏处理某个事件"能在编译期被发现。

type StreamEvent = | { : 'start'; messageId: string } | { : 'text-delta'; delta: string } | { : 'usage'; inputTokens: number; outputTokens: number } | { : 'error'; code: string; message: string } function handle(e: StreamEvent) { switch (e.) { case 'start': return init(e.messageId) case 'text-delta': return append(e.delta) case 'usage': return record(e.inputTokens, e.outputTokens) case 'error': return showError(e.code) default: const _never: = e return _never } }
  • 判别字段名（所有分支共用的那个字段）
  • switch 判断的字段
  • 用于穷尽性检查的类型（所有分支都处理完后剩下的类型）

项目一 · 知识库问答系统的后端骨架

这一课给整个项目定下类型骨架：StreamEvent 判别联合、zod schema 单一来源、Result 表达业务失败。后面的 RAG 检索、Agent 工具调用，全部复用这三样。

这一课要做的
  1. 把 StreamEvent 类型定义落到 src/types/stream.ts，前端消费端用 switch + never
  2. 用 zod 重写所有请求体校验，用 z.infer 替换手写 interface
  3. 给 note service 加 Result 返回值，错误用字面量联合而不是字符串
  4. 打开 noUncheckedIndexedAccess，修完所有报错（会抓出真 bug）
  5. 在 CI 里加 tsc --noEmit 和 eslint --max-warnings 0
完成标志：tsc --noEmit 零错误；新增一个 StreamEvent 类型时，前端 handleEvent 立刻编译报错；请求体校验和类型定义是同一份代码。
