第 21 课 · 实战 · 约 60 分钟

AI Coding：从"帮我写个函数"到"按规范交付"

AI 生成的代码不是免费劳动力，是"需要被审查的初级同事的输出"。

0/6 步 · 0%
学完你能

能建立一套让 AI 产出可直接进主干的流程：规格、上下文、验证、审查四步闭环。

前置知识
  • 有至少一个月的 AI 辅助编码经验
  • 有自己的项目，能跑测试和类型检查
  • 学过第四课，理解类型系统能挡住什么
本课 6 个学习目标
  1. 区分 AI Coding 的三个层次，知道自己现在在哪一层
  2. 给 AI 正确的上下文（仓库地图、约定、范例），而不是只说"帮我改一下"
  3. 用规格驱动的方式把模糊需求变成可验收的任务
  4. 建立验证闭环：类型、测试、lint、CI 四道闸
  5. 用正确的方法审查 AI 生成的代码，抓住它特有的错误模式
  6. 写一份团队级 AI 使用规范，说清什么能交给 AI、什么不能
第 1 / 6 步

三个层次：你在哪一层

层次形态AI 的角色你的角色产出质量
L1 补全编辑器里 Tab 补全猜下一行写全部逻辑取决于你
L2 对话式贴一段代码说"帮我改成 X"局部改写判断对不对、贴回去取决于你的审查
L3 规格驱动给 spec + 约束 + 验收标准，AI 改多个文件并自测执行者写规格、审结果、定标准取决于规格和验证

大多数人在 L2 就停了：让 AI 改一个函数，复制粘贴，跑一下没报错就提交。这个模式的天花板很低，因为你仍然是瓶颈——每一行都要你读、你判断、你粘贴。

L3 的关键变化不是"AI 更强"，而是你把工作重心从"写代码"移到了"写验收标准"。这和你带一个初级工程师是一样的：你不会给他一段代码让他改，你会给他一个任务、约束、验收条件，然后 review 结果。

★一个判断标准

"如果这段代码是一个实习生写的，我敢不敢直接合并？" 不敢，就说明缺了验证环节。L3 不是"更信任 AI"，而是"建立了不依赖信任的机制"——类型检查、测试、lint、CI。机制到位了，谁写的就不重要了。

前端经验类比
和 code review 对照

你 review 同事的 PR 时，看的是"这个改动是否符合我们的约定、有没有测试、边界处理了没"。review AI 的产出应该用完全一样的标准，而不是"看起来对就行"。降低标准是 AI Coding 最大的风险来源。

阶段项目

项目一 · 知识库问答系统：AI 协作规范

这一课不写业务代码，产出的是"怎么让 AI 帮你写这个项目"的规范与工具链——它会加速后面所有课的开发。

这一课要做的
  1. 写一份 AGENTS.md：技术栈、目录结构、必须遵守的约定、反例、不要做的事
  2. 把四道闸做成一条命令 `npm run check`（typecheck + lint + test + build）
  3. 实现 lintDiff 并接进 CI：禁止 as any / @ts-ignore / eslint-disable / 空 catch / skip 测试
  4. 用规格驱动的方式做一个真实需求：先写 spec（含验收断言）→ 让 AI 出 plan → 你审 → 拆 tasks → 逐个执行
  5. 练习"先写测试再写实现"：让 AI 写测试，你审，再让它实现；然后故意改坏实现验证测试会红
  6. 写一份团队 AI 使用规范：什么可以做、什么必须人工把关、什么禁止、PR 要写什么
完成标志：拿一个中等需求跑完整流程，记录"AI 生成 / 人工修改 / 返工"的行数比例；CI 能挡住一次故意加的 `as any`；团队里其他人能照着 AGENTS.md 让 AI 产出风格一致的代码。
