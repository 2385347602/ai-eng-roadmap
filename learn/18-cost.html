第 1 / 6 步

成本不是"单价 × token 数"这么简单

因为账单里有六项，你通常只算了第一项：

成本项占比（典型）容易被忽略的原因
输入 token35~50%主要成本，但常被低估（上下文比想象的长）
输出 token25~40%单价是输入的 2~4 倍
重试5~15%失败的调用也要付费
缓存未命中隐性本该命中却每次都重算
闲置/空转5~10%轮询、心跳、超时后仍在跑的请求
检索与工具5~10%embedding、rerank、OCR、ASR 都是钱
ts把六项都算进去
type Usage = {
  inputTokens: number
  cachedTokens: number      // 命中 prefix cache 的部分
  outputTokens: number
  retries: number
  embeddingTokens?: number
  rerankCalls?: number
}

function realCost(u: Usage, p: Pricing) {
  const freshInput = u.inputTokens - u.cachedTokens

  const input = (freshInput / 1e6) * p.inputPerM
  const cached = (u.cachedTokens / 1e6) * p.inputPerM * (p.cacheDiscount ?? 0.1)
  const output = (u.outputTokens / 1e6) * p.outputPerM

  // 重试是"白花的钱"：它不产生额外价值
  const retry = u.retries * (input + output) * 0.6

  const embed = ((u.embeddingTokens ?? 0) / 1e6) * p.embedPerM
  const rerank = (u.rerankCalls ?? 0) * p.rerankPerCall

  return { input, cached, output, retry, embed, rerank,
           total: input + cached + output + retry + embed + rerank }
}
!重试是纯损耗

一次成功的调用产生价值，一次失败的重试只产生账单。重试率从 3% 涨到 15%，成本直接多 10%，而用户什么也没得到。 所以"降低重试率"本身就是降本手段——超时设合理、错误分类清楚、限流做好，比换模型有效。

还有一个常被忽略的：超时后仍在跑的请求。用户关掉页面，你的流式生成还在继续，直到 max_tokens 才停。第十二课讲过要 abort，这里补上它的成本意义：一个 4000 token 的输出，跑到一半被放弃，那 2000 token 已经付过钱了。

阶段项目

项目一 · 知识库问答系统：降本一轮

这一课产出一份可验证的降本报告：成本从 X 降到 Y，质量没有下降，并且有数据支撑每一步的贡献。

这一课要做的
  1. 用 trace 数据算出当前六项成本的占比，找出真正的大头
  2. 统计每个 chunk 的"展示次数 / 被引用次数"，删掉引用率 < 2% 的材料，重跑评测
  3. 把 system prompt 里所有动态内容移到末尾，测 prefix cache 命中率变化
  4. 给输出加 max_tokens 上限和"简洁"约束，测输出 token 变化和用户满意度
  5. 实现语义缓存（三道护栏：无可变事实、同权限域、实体一致），测命中率和错误率
  6. 实现级联：小模型先答 + checkQuality 自检，测升级率和综合成本
  7. 实现多层预算：用户日/月、租户月、全局日，验证超额时正确拒绝或降级
  8. 算出单位经济：每个工单多少钱、人工多少钱、真实节省多少
完成标志：能拿出一张表：每项改动的成本贡献、质量影响、实施成本；总成本下降 50% 以上而评测通过率不降；能报出"每个工单 $0.032，人工 $2.4，自动化率 62%，净节省 $1.32/工单"这样的数字。
