上下文窗口不是记忆。窗口是"这一次能看到什么"，记忆是"下一次还能想起什么"。

第 1 / 7 步

三种记忆，三种存法

"记忆"这个词被用得太泛。工程上必须拆开，因为三种记忆的存储位置、召回方式、生命周期完全不同。

类型是什么存哪怎么召回活多久
工作记忆当前这轮对话的上下文messages 数组全量喂给模型本次会话
情节记忆发生过什么（"上次他说预算 5 万"）事件表 / 对话摘要按时间 + 相关性召回数周到数月
语义记忆关于用户/世界的事实（"他是财务负责人"）结构化档案 + 向量按实体或相似度召回长期，直到被推翻

这个区分解决了一个常见困惑：为什么我明明把历史都存了，模型还是"不记得"？ 因为存下来 ≠ 召回。工作记忆受窗口限制，情节和语义记忆需要主动检索才有用。

前端经验类比
和前端状态管理对照

工作记忆像组件内的 ref——只在当前组件活着的时候有效。情节记忆像 Pinia 的 action 历史——能回放，但要主动查。语义记忆像持久化到 localStorage 的偏好设置——跨会话存在，但需要显式读取才有用。三者混成一个 store，就是灾难。

★先问一个产品问题

在设计任何记忆之前，先回答："如果它记得这件事，用户会觉得贴心还是毛骨悚然？" 记得"他偏好简短回答"是贴心；记得"他上周三凌晨问过离婚协议"是毛骨悚然。这个判断决定了你的记忆边界，比任何技术选型都重要。

阶段项目

项目一 · 知识库问答系统：记忆层

这一课给项目加一层克制的记忆：只记"用户偏好卡片"和少量情节摘要，全部用户可见可删。不做自动事实抽取，先把最小闭环跑通。

这一课要做的
  1. 建三张表：user_prefs（用户显式设置）、session_state（目标/约束/已排除）、episodes（情节摘要，带 expiresAt）
  2. 实现 buildContext：钉住状态 + 中期摘要 + 最近 8 轮原文，替换掉原来的全量历史
  3. 实现记忆面板页面：列出所有记住的信息，支持编辑和删除（删除要跨表 + 清缓存）
  4. 实现时间衰减打分（半衰期 30 天），并给"硬约束"类记忆加必带通道
  5. 实现过期清理任务：episodes 到期自动删，置信度低于阈值的转"待确认"
  6. 做一次对照实验：同一批多轮对话，比较"全量历史"和"三层结构"的 token 消耗与回答质量
完成标志：能报出"上下文 token 下降 62%，回答质量（人工评）没有下降"；在记忆面板里删掉一条偏好后，下一次对话里系统确实不再引用它。
