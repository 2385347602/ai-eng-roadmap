第 1 / 7 步

为什么传统日志在 LLM 应用里失效

传统 Web 服务的日志模型是"一次请求一条记录"：GET /api/orders 200 43ms。出问题时，你顺着这条记录往下看错误栈就够了。

LLM 应用不是这样。一次用户请求，内部可能是：

一次请求，十几个可失败的点
POST /api/ask
 ├─ embed(query)                     ← 可能超时，可能返回零向量
 ├─ vector_search + keyword_search    ← 可能权限过滤误杀，可能索引过期
 ├─ rrf + rerank                      ← 可能 rerank 服务降级
 ├─ build_prompt                      ← 用了哪个版本？材料怎么排的？
 ├─ llm(stream)                       ← 可能 429，可能截断，可能拒答
 │   └─ usage: 3,812 in / 402 out     ← 花了多少钱？
 ├─ validate_output                   ← schema 过没过？重试了吗？
 └─ save_message                      ← 存的是原文还是脱敏版？
问题传统日志能回答吗为什么
这次回答花了多少钱不能没有 usage 记录
用的是哪版 prompt不能prompt 在代码里，日志里没有版本号
检索到了哪几个 chunk不能中间结果不落日志
为什么这次答得比上次差不能没有可对比的两次调用快照
哪个功能在烧钱不能成本没有归因维度
延迟高在哪一段部分能只能看到总耗时，看不到 prefill / decode / rerank 分布
★这一课的核心目标只有一个

给你一条 message id，能在 5 分钟内还原出：谁问的、检索到什么、用了哪版 prompt、模型返回什么、花了多少钱、每一步耗时多少。 做不到这一条，其他所有优化都是盲改。

前端经验类比
和前端埋点对照

你在前端埋点时会记 page_view、click、error，还要带 userId、sessionId、pageVersion，为的是"用户报了个 bug，能顺着 session 回放"。LLM 的 trace 就是同一件事，只不过回放的不是点击，而是一次推理的完整输入输出。

算清一次调用的成本

某次调用：输入 12,000 token（其中 8,000 命中 prefix cache），输出 900 token。输入单价 $0.5/百万 token，缓存命中按 10% 计价，输出单价 $1.5/百万 token。算出这次的成本。

未命中输入 = 12000 - 8000 = token 未命中成本 = 4000 × 0.5 / 1e6 = $ 命中成本 = 8000 × 0.5 × 0.1 / 1e6 = $ 输出成本 = 900 × 1.5 / 1e6 = $ 总成本 = $ 其中输出占比 = % 结论：这次调用里， 是主要成本
  • 未命中输入 token
  • 未命中输入成本
  • 缓存命中成本
  • 输出成本
  • 总成本
  • 输出占比（保留整数）
  • 哪一部分是主要成本

阶段项目

项目一 · 知识库问答系统：可观测层

这一课给项目装上"黑匣子"。做完之后，任何一次回答都能被还原：谁问的、搜到什么、用了哪版 prompt、花了多少钱、慢在哪。

这一课要做的
  1. 建 llm_spans 表（trace_id, span_id, parent_id, name, duration_ms, attrs jsonb），写 withSpan 包装函数
  2. 用 AsyncLocalStorage 实现父子关系自动传递，把 retrieve / rerank / llm.generate / validate 都包成 span
  3. 实现白名单 + 正则兜底的脱敏，落库前只保留安全字段和 200 字脱敏摘要
  4. prompt 改为文件加载 + 内容哈希版本号，把 prompt_version 记进 span
  5. 写三个成本查询：按 feature、按用户异常、按 prompt 版本对比
  6. 做一个 /admin/trace/:id 页面（或 CLI 命令），输入 trace_id 输出完整的树形时间线
  7. 实现告警规则：连续 5 个窗口错误率 > 5%、成本是昨日同时段 2 倍、拒答率突增
  8. 在用户侧加"报告问题"入口，自动带上 trace_id
完成标志：给一个 message id，能在两分钟内说出"这次检索命中了 3 条但都不含退款政策，prompt 用的是 qa_answer@3f9c1a2b，输入 3812 token 里 2048 命中缓存，总共花了 $0.0038"；成本面板能指出"agent_chat 这个功能占了 78% 的成本但只有 9% 的调用量"。
