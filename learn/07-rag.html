第 7 课 · 进阶 · 约 80 分钟

RAG 检索增强：把"模型不知道"变成"搜得到、答得准"

RAG 的 90% 问题出在检索，不在生成。而绝大多数人只调 prompt。

0/8 步 · 0%
学完你能

能独立设计一套可测量召回率的检索链路，并说清每个环节失效时该怎么定位。

前置知识
  • 学过第五、六课，理解 token、上下文窗口和 prompt 结构
  • 用过至少一个向量数据库或 pgvector
  • 手上有一批真实文档（产品手册、内部 wiki、合同、工单都行）
本课 7 个学习目标
  1. 说清 RAG 到底解决什么问题，以及它不解决什么问题
  2. 按文档结构切分，而不是按固定字数硬切
  3. 判断一个场景该用向量检索、关键词检索，还是两者都要
  4. 用 RRF 融合多路召回，并解释为什么它比调权重靠谱
  5. 把"答错了"拆成"没搜到"和"搜到了没答对"两种故障
  6. 把权限过滤下沉到检索层，避免越权召回
  7. 设计增量索引和拒答策略，让系统知道自己不知道
第 1 / 8 步

RAG 解决的不是"模型不知道"，是"模型不该猜"

新手对 RAG 的理解通常是"模型不知道我们公司的事，所以把文档喂给它"。这个理解不算错，但它会让你在错误的层面优化——你会以为 RAG 是个"喂资料"的动作，实际上 RAG 是一个检索系统 + 一个填空系统，而且前者决定了后者的上限。

更准确的理解：RAG 是把"开放域生成"降级成"给定材料下的阅读理解"。 模型不再需要从参数里回忆事实，只需要在你给的材料里找答案、组织语言。这一步降级同时解决了三件事：

问题不接 RAG 会怎样接 RAG 后
私有知识模型完全没听过，只能编材料在上下文里，有据可依
知识过期训练截止日之后的事一概不知改文档即生效，不用重训
无法溯源"我记得是……" 但给不出出处每句能挂到具体 chunk 和链接
权限隔离无解，模型不知道谁在问检索时按用户身份过滤
!RAG 不解决的问题

RAG 不会让模型变聪明。如果问题需要推理、计算、多步规划（"对比这三份合同的责任条款差异并给出风险等级"），检索只是把材料摆上桌，推理仍然靠模型本身。材料对了但模型推不出来，那是模型能力问题，加更多文档没用。

前端经验类比
和 Vue 的 computed 对照

RAG 像 computed：依赖（文档）变了，结果自动重算，你不用改组件代码。而把知识写进 prompt 像把值硬编码在 data() 里——改一次要重新部署一次，还改不干净。RAG 的本质是把"知识"从"代码"里解耦出来。

阶段项目

项目一 · 知识库问答系统：检索链路

这一课把项目从"能调模型"推进到"能查资料"。产出物是一个可测量 Recall@k 的检索服务，后面的评测课、可观测课都会拿它当被测对象。

这一课要做的
  1. 选 20 份真实文档（产品手册/内部 wiki/合同都行），按标题结构切分并入库
  2. 建 pgvector 表 + HNSW 索引 + tsvector 索引，实现向量与关键词双路召回
  3. 实现 RRF 融合，再接入一个 rerank 模型，把 top-50 压到 top-5
  4. 手工标注 20 个问题及其正确 chunk，跑出 Recall@10 和 MRR 基线数字
  5. 把权限过滤写进 SQL 的 where 条件，并用两个不同权限的账号验证不会越权召回
  6. 实现幂等增量索引：重复推送同一文档不产生重复块、不重复调 embedding
  7. 加拒答：top-1 rerank 分数低于阈值时直接返回"资料中没有相关内容"
完成标志：能报出"Recall@10 = 0.86，MRR = 0.61"这样的数字；把块大小从 800 调到 500 后重跑，能看到数字上升或下降；换一个低权限账号检索，返回结果里没有一条他无权看的文档。
