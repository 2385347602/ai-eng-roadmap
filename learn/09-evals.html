改一次 prompt 就说"感觉好多了"——这是玄学，不是工程。

第 1 / 7 步

"感觉变好了"是怎么骗你的

这是一个真实发生过很多次的事故模式：

  1. 你改了一版 prompt，手工试了 5 个问题，4 个明显变好，1 个差不多。判断"改进了"。
  2. 上线。三天后客服反馈"答非所问变多了"。
  3. 你回看日志，发现新版本在长问题和含否定词的问题上系统性变差——而你试的那 5 个都是短问题、肯定句。
  4. 更糟的是：你没法证明到底是这版 prompt 造成的，还是模型供应商偷偷更新了模型。

这个模式里有三个独立的错误：样本太小（5 条不足以下结论）、采样有偏（都是你自己想得到的问题）、没有基线（没有历史数字可对比）。评测体系就是修这三个错误。

★一句话原则

任何"改进了"的结论，都必须能说出：在多少条样本上、从多少提升到多少、用的是什么指标。 说不出来，就还没验证。

前端经验类比
和前端性能优化对照

你不会说"我感觉加了 will-change 之后顺滑了"，你会开 Performance 面板录一段，看 FPS 从 42 到 58。LLM 应用的评测就是它的 Performance 面板——只不过帧率换成了准确率，录制换成了黄金集。

算一次分层指标

50 条用例。检索层：40 条的正确 chunk 出现在 top-10 里。生成层：这 40 条里有 32 条回答忠实（每个断言都有依据）。端到端：全部 50 条里有 30 条被判定正确。填出三个指标。

Recall@10 = / 50 = (%) 忠实度 = 32 / = (%) 端到端准确率 = 30 / 50 = (%) 诊断：Recall 偏低 → 先修；忠实度 → 生成层尚可

  • Recall 百分比（整数）
  • 忠实度的分母（检索命中的条数）

编程挑战20 分练习 4 / 4

实现回归门禁

实现 gate(run, baseline, opts)。run 和 baseline 是 [{caseId, pass, error?}]。返回 { ok, reason?, delta }。规则：① 排除带 error 的条目（环境问题不算质量退化）；② 通过率跌幅 > opts.maxDrop（默认 0.03）判失败；③ 任何 opts.critical 里的用例从通过变失败，直接判失败。

阶段项目

项目一 · 知识库问答系统：评测体系

这一课让项目从"能跑"变成"能改"。产出物是一套 50 条的评测集 + 分层指标脚本 + CI 门禁，后面每一课改动都要过这道闸。

这一课要做的
  1. 从真实日志采样 50 条用例（含 10 条应拒答的负例、5 条历史失败案例），脱敏后存成 JSONL
  2. 给每条标注 goldChunkIds、mustInclude、mustNotInclude、expectedAction、tags、notes
  3. 实现分层评测脚本：Recall@10、MRR、忠实度（逐句二值判定）、格式合规率、端到端准确率
  4. 实现 LLM-as-judge 的 pairwise 对比（交换顺序跑两次，不一致判平局）
  5. 用 30 条人工标注校准 judge，算一致率，低于 75% 就改 judge prompt
  6. 实现回归门禁：排除 error、对比基线、关键用例一票否决
  7. 接进 GitHub Actions，PR 上自动跑并把结果贴成评论
  8. 留 20 条 holdout，只在发版前手动跑
完成标志：随便改一版 prompt，能在 10 分钟内拿到"Recall 0.86 / 忠实度 0.91 / 端到端 0.78，比基线 +4 个点，无关键用例退化"这样一份报告；故意改坏一处（比如把检索 top-k 从 10 降到 3），门禁能红并指出退化的是哪几条。
