分层与依赖注入：把 90 行拆成能被三个人同时维护的结构

分层不是把文件放进不同文件夹。它是"依赖只能朝一个方向流动"这条规则。

0/8 步 · 0%
学完你能

能独立判断一个模块该拆成几层、每层放什么、什么情况下不该拆，并手写一个依赖注入容器。

前置知识
  • 学过第一课，知道 req / res 是什么
  • 用过 class 和 interface
  • 能看懂 async / await
本课 6 个学习目标
  1. 说清分层的本质是依赖方向，而不是目录结构
  2. 把一个混在一起的 handler 拆成 controller / service / repository 三层
  3. 解释 new 为什么是问题，以及依赖注入解决的三个具体痛点
  4. 手写一个 40 行的 DI 容器，含单例、循环依赖检测
  5. 判断什么时候不该分层，识别过度抽象的三种症状
  6. 不启动 HTTP 服务器就能测业务逻辑
第 1 / 8 步

先看清楚：90 行之后会发生什么

第一课那份 90 行的 server.ts 是能跑的。问题不在于它错，而在于它只能停在 90 行。一旦变成 900 行，会出现三个具体的痛，而且这三个痛都不是"代码不好看"这种审美问题。

痛具体表现后果
改一处要读全文加一个字段要动 readJson、校验、组装、序列化四段改错概率随行数线性上升
没法单独测业务逻辑和 req/res 绑死，测一个"余额不足"要起 HTTP 服务、造请求、解析响应测试慢到没人愿意写
换实现要动业务从内存换 SQLite、从 SQLite 换 Postgres，业务代码跟着改技术选型被锁死

分层要解决的正是这三件事。注意它不解决"代码变多"——分层之后文件数会变多，总行数也会略微上升。如果它只让代码变多，那确实是过度设计。它换来的是：改动的影响范围可预测。

前端经验类比
和 Vue 的组件拆分对照

你把一个 800 行的页面拆成 12 个组件，不是为了行数变少，而是为了让"改价格显示"只动 PriceCard，不碰其余 11 个。分层做的是同一件事，只不过拆的维度是"职责"而不是"界面区域"。

i一个判断标准

如果你改一个需求，需要同时打开三个以上文件才能确认改对了，那说明职责边界划错了。好的分层让"改一个需求"落在 1~2 个文件里。

错误排查20 分练习 3 / 4

找错：这个 service 有三处越界

下面这段代码放在 application/note.service.ts 里。它违反了分层规则，也埋了两个 bug。找出所有问题。

export class NoteService {
  async rename(req: IncomingMessage, res: ServerResponse) {
    const id = req.url!.split('/').pop()!
    const body = await readJson(req)

    const note = await this.repo.findById(id)
    if (note.userId !== req.headers['x-user-id']) {
      res.statusCode = 403
      return res.end('forbidden')
    }

    note.title = body.title
    await this.repo.update(note)
    res.statusCode = 200
    res.end(JSON.stringify(note))
  }
}

项目一 · 知识库问答系统的后端骨架

这一课要做的
